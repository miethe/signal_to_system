## The fix existed. The projects were still wrong.

The reviewer was supposed to check the work. First I had to check the reviewer.

A reviewer skill used across my projects was missing a mandatory guard, so I fixed it at the source: the `/.claude/skills/` directory in my most active project. My personal registry showed the fixed version. Inside the source repository, the reviewer (obviously) had the new instruction, but every other project on the machine loaded a deployed file copy, and that copy sat five days without the fix.[^drift]

<ThreadScene slug="the-registry-wave-agentic-artifact-supply-chain" beatId="incident" composition="pane" />

The registry was right. The copy the runtime loaded was wrong. Nothing said so, because nothing compared the deployed bytes to the registered ones.

<PullQuote variant="thesis-marker">Trusted artifact ≠ trusted use.</PullQuote>

Approval attaches to an artifact; use happens in a context the approval never saw. Even after I correct the copy (`task-completion-validator`, the reviewer skill from the opening), I still need to know who may use it, with which tools and context, what actually ran, and whether the review met its purpose.

The system lied in four increasingly important ways: “fixed” did not mean deployed; the same name did not mean the same artifact; present did not mean followed; traceable did not mean successful. The stale reviewer only proves the first lie. It gave me a clean place to see the others.

## The harder problem: not every difference should disappear.

A stale copy is the easy failure. The harder case is a different copy that is different on purpose. If one project has a useful local improvement, blindly replacing it with the shared version is also wrong. The supply-chain problem is not making every copy identical. It is knowing which differences are stale, which are deliberate, and which should become shared improvements.

<div class="managed-variation" role="group" aria-label="Illustrative managed variation comparison">
  <div>
    <strong>Project A: behind</strong><br />
    Its declared binding is newer than the deployed copy. Update it, then record the comparison.
  </div>
  <div>
    <strong>Project B: useful local improvement</strong><br />
    Its copy carries a local delta. Inspect it, reconcile it, and preserve it until a shared decision says otherwise.
  </div>
  <div>
    <strong>Project C: deliberate older pin</strong><br />
    Its older version is the declared state for an experiment or policy boundary. Preserve the pin until that boundary changes.
  </div>
</div>

This is illustrative, not three recorded lab incidents. The decision is not a security waiver, and “preserve” does not mean “approve forever.” It means a system should be able to distinguish an accidental stale copy from an accountable difference before a synchronization command erases either one.

Preserving Project B's patch keeps the evidence available, but that doesn't approve the patch for everyone. A useful local change can become a candidate for shared policy; it shouldn't automatically become shared policy simply because a sync command happened to encounter it. Project C's pin can travel the other way and become ineligible under a changed requirement. Both are policy questions in this example, not lab incidents I have recorded. What I want from the supply chain is that a shared correction reaches every destination that should have it, and stops at the one that shouldn't.

<PullQuote>The goal is not one approved copy everywhere. It is knowing which differences are stale, which are deliberate, and which should become shared improvements.</PullQuote>

<ThreadScene slug="the-registry-wave-agentic-artifact-supply-chain" beatId="deployment" composition="pane" />

The remedy is a recorded, registry-driven deployment. No manual copy/paste, no symlink as a shortcut around the record. A symlink follows the source checkout as branches change, so it drifts with the branch instead of leaving stale bytes behind. Multiple git worktrees make this worse, as each checkout silently maintains its own artifact state. Either way, “it's the same skill” conceals the state that matters.

<ThreadScene slug="the-registry-wave-agentic-artifact-supply-chain" beatId="use" />

That last distinction matters once the corrected copy is actually deployed. A guard can be present in the file an agent loads and still not be followed in a specific run. I do not have a per-session record for the stale-reviewer incident, so this is a conceptual branch, not a claim about what that reviewer did.

## What the registry wave actually solved.

I didn't start here by defining a new category. Like most good (engineering) stories, it started with an annoyance, and the desire to be lazy.

It was mid-late 2025 when I started building <Term id="skillmeat">SkillMeat</Term>, my registry and deployment tool for reusable agent capabilities. Getting useful behavior once was no longer the hard part. Making that behavior repeatable across projects, machines, teams, and runtimes was. Good agent behavior is a bundle: instructions, context, assumptions, examples, tools, permissions, and review expectations.

<PullQuote>Copy and paste is fine for discovery, but it will never be a lifecycle.</PullQuote>

A registry answers useful questions: where do I find this skill, how do I install it, what version am I using, and where did it come from? The current wave of registries and catalogs is real, even if the responsibilities are unevenly joined. GitHub's `gh skill` remains a public-preview command surface; JFrog documents an available registry with optional, tier-dependent signing and a Preview boundary on the relevant local enforcement; Red Hat documents separate pre-GA Agent Catalog and MCP Catalog roles; the official MCP Registry is a preview metadata and discovery service, not an enforcement point.[^github][^jfrog][^redhat][^mcp]

Give the thing a concrete shape for a second: a skill, command, context pack, policy, hook, or tool definition. An artifact is small enough to install and large enough to carry intent. A registry makes its identity and distribution legible. It cannot establish that the version a runtime loaded still matches the approved one, much less that its use was authorized or its outcome was accepted.

## From artifact to use.

The registry wave makes the first record easier to manage. The architecture problem begins at the handoffs: source to declared binding, binding to deployment, deployment to runtime loading, runtime activity to verification, verification to an acceptance decision.

For five days, “fixed” described one location.[^drift]

## The handoffs are the architecture.

The useful model is not a hierarchy where each layer owns exactly one responsibility. These are participating surfaces. Registry and distribution dominate artifact lifecycle; runtime gateways and policy systems dominate authorization; orchestration carries work across boundaries; evidence systems correlate what happened. The fabric is the shared identity and evidence that survives those handoffs.

<PullQuote>A configured integration is not enforcement; an advisory registration is not a gate.</PullQuote>

Four boundaries stay distinct even when the same product participates in more than one of them:

A known source can deliver a harmful artifact. Permitted work can still be wrong. A run using a skill does not establish that the skill caused the result. Fixed dependencies do not make probabilistic reasoning deterministic. The next question is whether the request, evidence, and authority survive long enough to judge the outcome. A <Term id="feature-contract">Feature Contract</Term> is one way to make those obligations explicit; [The Contract Is the Work](/essays/the-contract-is-the-work/) takes up that boundary.

<ThreadScene slug="the-registry-wave-agentic-artifact-supply-chain" beatId="outcome" composition="pane" />

This is where the fourth lie gets expensive. The September audit found automatic BOM emission on bundle materialization, while a separate single-artifact deployment path emitted activity events without invoking that writer.[^bom-scope] Another audit inspected three real context-provenance records but could not identify whether a human or automated actor wrote them.[^context-records] A record exists. Its claimed meaning still needs a boundary.

## What I can prove today.

<ClaimBadge kind="observed" /> Local deployment checks can compare declared and deployed artifacts, distinguish tracked and allowed copies, and surface undeclared ones. <ClaimBadge kind="measured" /> A scoped audit found the two provenance gaps above. <ClaimBadge kind="proposed" /> The complete chain from loaded artifact version through context, policy, observed actions, verification, and an acceptance decision is still a design target, not a measured closed loop.

The retained September 15 run of the same gate exited nonzero on a different, unrelated undeclared-copy finding. That is useful evidence that the gate can surface a real problem. It is not a replay of the stale reviewer, and it does not tell me what any past agent session loaded.

I place this work within the emerging discipline of <Term id="agentic-systems-engineering">**Agentic Systems Engineering**</Term>, already named in academic work by Sun and colleagues and in enterprise work by OutSystems.[^ase] This series examines my particular architecture through the systems I build and the failures they expose. Agentic SDLC is its application to software delivery. This reading path connects the questions; it isn't a one-to-one map of architecture layers.

The reviewer didn't need a better name or another catalog. It needed the fix to reach the place that loaded it, a check that noticed when it hadn't, and evidence that the resulting review did what was asked. It also needed room for a project-specific improvement to survive the next shared correction. That's the bar I want the supply chain to meet when I'm no longer watching every project myself.

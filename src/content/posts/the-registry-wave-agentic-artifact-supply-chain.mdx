The reviewer was supposed to check the work. First I had to check the reviewer.

<ThreadBeat slug="the-registry-wave-agentic-artifact-supply-chain" beat="incident" />

A reviewer skill used across my projects was missing a mandatory guard, so I fixed it at the source: the `/.claude/skills/` directory in my most active project. My personal registry showed the fixed version. Inside the source repository, the reviewer (obviously) had the new instruction, but every other project on the machine loaded a deployed file copy, and that copy sat five days without the fix.[^drift]

Same skill name, but different instructions reaching the runtime.

The registry was right. The copy the runtime loaded was wrong. Nothing said so, because nothing compared the deployed bytes to the registered ones.

What exactly did the approval attach to?

**Trusted artifact ≠ trusted use.** Approval attaches to an artifact; use happens in a context the approval never saw. Even after I correct the copy (`task-completion-validator`, the reviewer skill from the opening), I still need to know who may use it, with which tools and context, what actually ran, and whether the review met its purpose.

The stale reviewer is the easy half. A separate incident handed me the hard half: some projects had fallen behind and needed the shared fix, others had edited the same file for their own good reasons. Push the correction everywhere and I repair the first group by deleting a protection from the second.

Some copies must change. Some differences must survive. Keeping track of which is which is the supply-chain problem this essay is about.

I didn't start here by defining a new category. Like most good (engineering) stories, it started with an annoyance, and the desire to be lazy.

It was mid-late 2025 when I started building <Term id="skillmeat">SkillMeat</Term>, my registry and deployment tool for reusable agent capabilities. Getting an agent to do something useful once was no longer the hard part. Making that behavior repeatable across projects, machines, teams, and runtimes was. Good agent behavior is a bundle: instructions, context, assumptions, examples, tools, permissions, and review expectations. When that bundle lived in one chat transcript or one local folder, it was fragile, and when another project needed it, the answer was usually copy and paste.

Copy and paste is fine for discovery, but it will never be a lifecycle.

## What the registry wave solved

A registry solves important problems.

Where do I find this skill? How do I install it? What version am I using? Where did it come from? Can I update it? Can I publish it?

Those questions matter. They are not the whole lifecycle. For my reviewer, the registry preserved the corrected artifact while the deployed copy fell behind. Having a source of truth made the discrepancy diagnosable.

What it couldn't tell me was whether any of those answers still described the file an agent actually loaded. The useful question is which assurances survive each handoff.

## Four assurances, four places to lose the thread

I use “Wave 1” and “Wave 2” here to distinguish responsibilities, not to rank vendors or predict a release sequence. A registry can participate in every row. It can't establish every answer from its own artifact record.

| Assurance | Wave 1: registry record | Wave 2: supply-chain obligation |
| --- | --- | --- |
| **Identity** | Names the artifact, version, source, and approval. Doesn't establish which bytes the runtime loaded. | Pins the artifact and dependencies; compares the deployed and loaded identity with the approved one. |
| **Conditions of use** | Records declared compatibility and approval scope. Doesn't establish whether this caller, context, or permission state still qualifies. | Binds use to a project, actor, context, tools, policy, and risk boundary; rechecks when those conditions change. |
| **Execution** | Records availability or deployment intent. Doesn't establish what actually ran. | Captures the loaded artifacts, runtime/model state, permitted actions, and observed tool activity within an execution envelope. |
| **Outcome** | Preserves evaluations or prior acceptance. Doesn't establish that this run fulfilled this request. | Connects output to intent, verification evidence, and the authority accepting or rejecting the result. |

The reviewer failed the first handoff: registered identity never reached the loaded copy. Fixing that closes one gap, but a correctly deployed reviewer could still receive stale project context, have inappropriate permissions, skip its guard, or approve the wrong thing.

Thus the enterprise question isn't "do we have a place to store these things?", as that's essentially a solved problem.

Rather, the question is "can we govern the lifecycle of the things that shape agent behavior?"

## What counts as an artifact

Give it a concrete shape for a second: a skill, a command, an agent definition, a memory item, a context pack, any reusable, versioned unit you can collect and deploy into a project.

Call that the <Term id="agentic-artifact">**agentic artifact**</Term>: whatever shapes how the agent reasons, acts, accesses tools, applies context, follows policy, or produces work.

The runtime executes. A skill shapes its behavior. Markdown instructions don't reason on their own, and a signed context pack doesn't enforce the permissions it describes.

Instruction, Tool, Context and Governance are the static side: the things an agent draws on. Execution is the runtime topology that selects which of them a session actually loads, and Evidence is what that session leaves behind.

| Artifact family | Examples | What needs versioning and review |
| --- | --- | --- |
| Instruction | Prompts, skills, commands, rules | Non-executable instructions and any bundled executable dependencies |
| Tool | MCP servers, scripts, API adapters | Executable implementation, tool declarations, and permission boundaries |
| Context | Context packs, memories, domain references | Non-executable inputs, provenance, freshness, and scope |
| Governance | Policies, approvals, evaluation sets | Declared constraints and the mechanisms that enforce or test them |
| Execution | Workflows, agent definitions, deployment bindings | The configuration selecting instructions, tools, and runtime conditions |
| Evidence | Manifests, run records, verification results | Retained observations and their links to artifacts and accepted work |

I use <Term id="agentic-artifact-supply-chain">**agentic artifact supply chain**</Term> for the managed lifecycle of those reusable instructions, context, tools, policies and related assets. Existing work on agent supply chains and governed agent primitives already covers this ground; this is my organizing label for the lifecycle I'm building, not a new supply-chain analogy.[^primitives]

Both executable code and non-executable context are versioned dependencies. Changing either can change runtime behavior. Freezing both makes the inputs inspectable; it doesn't freeze the model's reasoning.

A skill is small enough to install and large enough to carry intent. It can tell an agent how to perform a task, when to use supporting scripts, which references matter, and which constraints should shape execution. We're talking about more than just a prompt; it's a capability bundle.

## Follow the reviewer out of the registry

The lifecycle starts with **authoring**: the reviewer lives in one source repository, and a fix adds the missing guard. **Registration** makes that revision discoverable. **Approval** needs to attach to an exact revision and state its permitted use. The incident doesn't give me evidence of a complete approval record; it gives me a corrected source and a registry entry that didn't match deployment.

<ThreadBeat slug="the-registry-wave-agentic-artifact-supply-chain" beat="deployment" />

**Deployment** is where I lost the thread. A file copy is a separate object. Updating its source doesn't update it, and a successful registration says nothing about the copy another project loads.

The remedy is a recorded, registry-driven deployment. No manual copy/paste, no symlink as a shortcut around the record. A symlink follows the source checkout as branches change, so it drifts with the branch instead of leaving stale bytes behind. Multiple git worktrees make this worse, as each checkout silently maintains its own artifact state. Either way, “it's the same skill” conceals the state that matters.

I need three separate answers: what the project intended to use, what is present on disk, and what the runtime actually used. A deployment check can establish the second without establishing the third. If a session started before the update, inspecting the file afterward won't tell me what it loaded. The run needs its own observation; absent that, the loaded version stays unknown.

At **use**, the project loads the deployed copy in its own context. The supply-chain obligation is to check that binding: the approved artifact, the expected context, and the allowed tools. The guard's presence is a prerequisite for the intended review, not evidence that the guard was followed.

At **drift**, declared and actual state separate. The fix stayed in the source repository while every project outside it kept loading the pre-fix reviewer. For five days, “fixed” described one location.

The manifest driving the drift gate classifies each deployed path into exactly one bucket: a diffed tracked copy, a never-diffed allowed copy, or an undeclared hard failure.

Two redacted entries show the distinction:

```yaml
# scripts/global-artifact-manifest.yaml

    tracks: agentic_meta_dev/infra/hooks/finding_filing_check.sh

      PostToolUse write-time nudge for unfiled findings. Migrated off a symlink to a plain
      copy per the no-new-symlinks doctrine; now diffed against upstream instead of going
      untracked.

  - path: ~/.claude/skills/building-readmes
    reason: No repo upstream anywhere under development/. Global is the only instance.
```

*One tracked copy, diffed against its upstream on every run, and one allowed copy, never diffed, because no upstream exists to diff against.*

At **detection**, a gate compares deployed state with its source. The August 6 drift check classifies deployed entries, distinguishing tracked copies, justified copies, and drift; it also identifies symlinks. Drift fails the check.[^drift] A justified copy needs an explicit reason to differ. Otherwise exceptions become another way to lose the deployment record.

The next correction handles **missing dependencies**. An artifact absent locally is *unprovisioned, not non-existent*. The provisioning rule directs the agent back to the registry. Its failure hook suggests the deploy command; it doesn't write the artifact itself.[^provisioning] Hand-rolling a replacement would recreate the problem under a new name.

Keep this loose and fast locally. I want to experiment with a skill before promoting it, much as I can edit a branch before CI checks a shared change. The gates belong at promotion and use boundaries where another project starts depending on the result. Automate the comparison and make a failed check explain the repair. A meeting to approve every local prompt edit would solve a different problem: ensuring nobody uses the system.

Replacement and revocation also need a destination list. If I retire the reviewer, I need to find its deployed copies and prevent further use. Deleting the registry entry alone would leave those copies behind.

A content hash answers whether bytes match a recorded revision. An ancestry record answers which base a local change came from. Neither tells me whether that change is useful, approved or compatible. I need the base to understand the patch, the current bytes to identify it, and review and tests to decide what should happen next.

That distinction is what the second incident turned on, the workflow copies rather than the reviewer. Some projects were behind upstream and missing review checks. Others had a stricter local check: they could refuse a conditional review verdict that upstream would accept. Copying upstream over every project would have repaired one group by deleting a protection from another. The synchronization tool is local lab tooling rather than a registry feature, and it inspects the direction of change, preserves the per-project agent roster, and refuses to overwrite local-ahead copies. Mixed changes need inspection.[^workflow]

Name the hops and the question changes shape. **Source:** the repository where the reviewer is authored and the guard was added. **Collection:** the registered set a project deploys from, holding the revision approval attached to. **Project:** the destination that holds a copy and loads it at runtime. Three objects, three separate facts: the revision a project intends to bind, the bytes actually present, and the version a run actually loaded. My checks establish the first two; the third needs a run record. That path is illustrative for one reviewer skill, not a claim that anything I run reconciles all three automatically.

<Callout type="info" title="Three projects, three different repairs">
Illustrative, not a production inventory. All three deploy the same reviewer skill name.

**Project A declares the corrected revision and still has the old bytes.** Repair the deployment; nothing here is worth preserving.

**Project B carries a local patch for its own review process.** Inspect the difference before replacing it, because a blanket update deletes a protection nobody reviewed.

**Project C deliberately pins an older revision for a bounded comparison.** The question isn't whether the pin is old; it's whether it's still allowed.

<details>
<summary>What each case needs before its repair is safe</summary>

A needs the intended revision and a byte comparison against it. B needs the patch's base, so the difference reads as a change rather than a mystery, plus an owner who can state what it assumes and which tests cover it. C needs the policy that authorized the pin, rechecked against current security and compatibility requirements. None of the three has a known runtime identity until a run record says what loaded.

</details>
</Callout>

Preserving Project B's patch keeps the evidence available, but that doesn't approve the patch for everyone. A useful local change can become a candidate for shared policy; it shouldn't automatically become shared policy simply because a sync command happened to encounter it. Project C's pin can travel the other way and become ineligible under a changed requirement. Both are policy questions in this example, not lab incidents I have recorded. What I want from the supply chain is that a shared correction reaches every destination that should have it, and stops at the one that shouldn't.

## A control fabric across many systems

“Control plane” is the familiar shorthand. But an enterprise will run many governance systems, with different owners and enforcement mechanisms. <Term id="control-fabric">**Control fabric**</Term> is established terminology, including BCG's federated agent-control framing. Here it names independently operated systems that preserve compatible identity, authority, policy-decision and evidence records across handoffs.[^fabric] I use it to connect four responsibilities:

| Responsibility | What it owes the reviewer workflow |
| --- | --- |
| **Supply chain** | Artifact identity, dependencies, recorded deployment, promotion, replacement, and revocation |
| **Runtime control** | Caller identity, current authorization, tool permissions, budgets, and enforcement during use |
| **Orchestration** | Routing the review, carrying its scope across handoffs, retries, and human decision points |
| **Evidence** | What ran, what it produced, what was verified, and who accepted it |

Four responsibilities, not four products, and they overlap: context is a governed dependency and an input to a runtime decision at once. Writing a policy under one of these headings doesn't establish that a runtime checks it, so I still need to name the mechanism in the execution path and what it blocks. My own <Term id="aos">Agentic OS (AOS)</Term> covers these unevenly. The table is the obligation, not a claim of coverage; they become a control fabric only once the handoffs carry identity and evidence.

Shared identity means the deployment record and run record can refer to the same exact artifact. Shared evidence means the next system can inspect what the previous one established. An explicit handoff says who checks the next condition and what happens when it fails.

A configured integration isn't enforcement; an advisory registration isn't a gate.

Xia and colleagues' *Harnessing Agent Skills* describes a closely related architecture: it separates the stored artifact from skill-in-use, mediates execution, retains run evidence and feeds results back into managed supply. It also includes a run-scoped Skill-BOM.[^xia] That overlap helps make the comparison concrete. My contribution here is the architecture I'm implementing around shared corrections and deliberate local variation, the deployment checks it produced, and the failures those checks expose. The dated records below support that implementation history. They don't yet establish a general improvement in delivery or a unique architecture.

## From deployed artifact to delivered outcome

The lab receipts establish narrower facts: a stale reviewer copy, a drift detector, and related checks for instruction parity and stale operating guidance. They don't establish a complete artifact-version-to-outcome measurement system.

<ThreadBeat slug="the-registry-wave-agentic-artifact-supply-chain" beat="outcome" />

In the model I want to build, closing that loop requires a run record that identifies which reviewer version was loaded, alongside the model, context, tools, and policy state. Join that record to the review's findings, verification, and acceptance decision. Then ask which runs used the old copy and which outputs need re-review. Where the loaded identity wasn't captured, mark the run's version unknown. Don't reconstruct certainty from the current registry.

<Term id="skillbom">**SkillBOM**</Term> already appears in research on skill identity, dependencies and run provenance.[^skillbom] Here it names this implementation's manifest for recording artifact composition and provenance. The useful question is which relationships it preserves. A manifest produced while assembling a bundle can identify the assembled artifacts without proving that a later session loaded them. A run record has to bind that use separately.

Failure rate needs a denominator and a definition: failed reviews among comparable tasks, failure decided by an explicit acceptance criterion. A lower rate after deploying the guard would be useful evidence. It still wouldn't isolate the guard if the model or task mix changed too.

Drift can also happen against a frozen skill. Keep its bytes unchanged and change the runtime or context; the same instructions may produce different behavior. Compare those runs separately from an artifact-version change. Otherwise the registry gets blamed for degradation it didn't cause, or credit for an improvement it didn't produce.

I want to measure accepted outcomes with evidence. For this reviewer, that means a review that meets the request, with evidence of the required guard and an authorized acceptance decision. A <Term id="feature-contract">**Feature Contract**</Term> makes those obligations explicit; [The Contract Is the Work](/essays/the-contract-is-the-work/) takes up that boundary.

<Callout type="info" title="Keep the assurances separate">
**Authenticity ≠ safety:** a known source can supply a harmful artifact.

**Authorization ≠ correctness:** permitted work can still be wrong.

**Traceability ≠ causal attribution:** a run using a skill doesn't establish that the skill caused its result.

**Pinned inputs ≠ determinism:** fixed dependencies don't make probabilistic reasoning deterministic.

**Accepted output ≠ business value:** fulfilling a review request doesn't establish that the larger delivery process improved.

The next essay considers the <Term id="deterministic-envelope">deterministic envelope</Term>, an existing way of describing constraints around probabilistic systems. My emphasis will be on controls outside model judgment and evidence that they mediate execution, alongside related work such as RAILS.[^envelope] Repeated successful reasoning can suggest a candidate for automation. It doesn't establish authority to promote it, or tell me when to withdraw it. Those remain questions to test.
</Callout>

## Where the system lied to us

Keeping those assurances separate is easy on a page; I only learned they don't stay separate in practice because my own tooling kept reporting one of them and letting me read it as another.

The drift-gate receipt records why the check was written at all: “the fix exists” had stood in for “the projects received the fix,” and my own artifact-management workflow let that substitution pass.[^drift]

The related August 5 parity gate followed six weeks of stale doctrine reaching one class of agent harness. A harness is the software that loads instructions and runs the agent. Updating one harness-specific instruction file hadn't updated its sibling.[^parity] The staleness check, two days later, searches live documents for assertions naming a superseded model as the operating “spine,” while exempting dated historical records.[^staleness]

These are detection mechanisms with different boundaries. Byte comparison catches the stale reviewer. Parity catches divergence between sibling instructions. The staleness check catches a particular outdated claim even when the files aren't supposed to be identical. But none proves that every remaining instruction is correct.

The same substitution showed up in provenance. In the September audit, SkillBOM emission was wired into bundle assembly. Deploying a single artifact used a different path and didn't automatically emit a BOM. Both operations could reasonably be described as deploying capability, but only one reached that evidence writer.[^bom-scope] A feature list saying “provenance supported” concealed the question I needed answered: supported on the operation I just performed?

Another context-provenance tool had produced three real records with deployed-artifact findings. The records existed; the CLI path that could write them existed too. What the durable record didn't establish was whether a human had run that command or an automated agent had invoked it.[^context-records] Production-shaped output, unresolved producer. I can't use those rows to claim autonomous reconciliation.

Even the comparison itself can ask the wrong question. A maintenance check rejected a report that a dependency's fix had shipped because the original commit wasn't an ancestor of the release. The repository squash-merges. Inspecting the tagged file showed the fix was present.[^ancestry] The ancestry result was correct; my conclusion about the release would have been wrong. A receipt needs a question as well as a timestamp.

These failures changed what I ask a registry to show me. I want a deployment record with a destination, a comparison against that destination's intended state, and a separate account of use. When one is missing, the other two shouldn't quietly fill in for it. A green registration result can't answer a loading question, and an output file can't identify its producer unless that identity was retained.

The retained September 15 run of the same gate exited nonzero, on a different and unrelated class of finding:

```
      another project's checkout.
      fix: register it via SkillMeat and/or declare it in the manifest, never symlink it.

```

**Implemented:** <Term id="meatywiki">MeatyWiki</Term>, my durable knowledge store, and <Term id="research-foundry">Research Foundry</Term>, my evidence-oriented research system, give context and evidence homes beyond the registry. <Term id="meatyprompts">MeatyPrompts</Term>, my earlier prompt-management experiment, was part of the path here.

## Receipts behind the argument

These are dated implementation records, summarized as methods. The August commits establish when checks entered the repository; the September audit establishes what that later inspection found. Neither date silently becomes the incident date or an attestation of today's runtime state.

<Evidence kind="observed" /> **The reviewer copy.** The drift-check source records a deployed reviewer missing its mandatory establish-the-diff step while the upstream copy contained it. I place this work within the emerging discipline of <Term id="agentic-systems-engineering">**Agentic Systems Engineering**</Term>, already named in academic work by Sun and colleagues and in enterprise work by OutSystems.[^ase] This series examines my particular architecture through the systems I build and the failures they expose. The reviewer didn't need a better name or another catalog.

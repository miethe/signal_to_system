First published July 2026; re-published September 15, 2026. This full September rewrite follows two external reviews and a failure in my own deployment process. The July argument centered on registries becoming supply chains. This edition sharpens the boundary: approving an artifact doesn't establish that a particular use is trustworthy. The distinction below is the September argument, not a claim about what the July essay already said.

**[Observed]** A reviewer skill used across my projects was missing a mandatory guard. I fixed the source. The personal registry showed the fixed version. Inside the source repository, the reviewer had the new instruction. Every other project on the machine loaded a deployed file copy, and that copy sat five days without the fix.[^drift]

Same skill name. Different instructions reaching the runtime.

The registry was right. The use was wrong. Nothing said so, because nothing compared the deployed bytes to the registered ones.

What exactly did the approval attach to?

**Trusted artifact ≠ trusted use.** That distinction is loadbearing (an inside joke for the Claude 5 model-family users). Approval attaches to an artifact; use happens in a context the approval never saw. Even after I correct the copy, I still need to know who may use it, with which tools and context, what actually ran, and whether the review met its purpose.

That is the supply-chain problem this essay is about.

I didn't begin this journey by defining a new category. Like most good (engineering) stories, it started with an annoyance, and the desire to be lazy.

It was mid-late 2025 when I started building SkillMeat, my registry and deployment tool for reusable agent capabilities. The hard part was not getting an agent to do something useful once. The hard part was making that behavior repeatable across projects, machines, teams, and runtimes. Good agent behavior was a bundle: instructions, context, assumptions, examples, tools, permissions, and review expectations. When that bundle lived in one chat transcript or one local folder, it was fragile. When another project needed it, the answer was usually copy and paste.

Copy and paste is fine for discovery, but it will never be a lifecycle.

**Prior question:** How does work survive the session? **This thesis:** artifact approval and trusted use require different evidence. **Next question:** what preserves the authoritative meaning of the work?

## What the registry wave solved

A registry solves important problems.

Where do I find this skill? How do I install it? What version am I using? Where did it come from? Can I update it? Can I publish it?

Those are real questions which demand good answers. For my reviewer, the registry preserved the corrected artifact while the deployed copy fell behind. Having a source of truth made the discrepancy diagnosable.

## Four assurances, four places to lose the thread

**[Proposed synthesis]** I use “Wave 1” and “Wave 2” here to distinguish responsibilities, not to rank vendors or predict a release sequence. A registry can participate in every row. It can't establish every answer from its own artifact record.

| Assurance | Wave 1: registry record | Wave 2: supply-chain obligation |
| --- | --- | --- |
| **Identity** | Names the artifact, version, source, and approval. Doesn't establish which bytes the runtime loaded. | Pins the artifact and dependencies; compares the deployed and loaded identity with the approved one. |
| **Conditions of use** | Records declared compatibility and approval scope. Doesn't establish whether this caller, context, or permission state still qualifies. | Binds use to a project, actor, context, tools, policy, and risk boundary; rechecks when those conditions change. |
| **Execution** | Records availability or deployment intent. Doesn't establish what actually ran. | Captures the loaded artifacts, runtime/model state, permitted actions, and observed tool activity within an execution envelope. |
| **Outcome** | Preserves evaluations or prior acceptance. Doesn't establish that this run fulfilled this request. | Connects output to intent, verification evidence, and the authority accepting or rejecting the result. |

The reviewer failed the first handoff: registered identity never reached the loaded copy. Fixing that closes one gap. But a correctly deployed reviewer could still receive stale project context, have inappropriate permissions, skip its guard, or approve the wrong thing.

Thus the enterprise question isn't "do we have a place to store these things?", as that's essentially a solved problem.

Rather, the question is "can we govern the lifecycle of the things that shape agent behavior?"

## What counts as an artifact

Give it a concrete shape for a second: a skill, a command, an agent definition, a memory item, a context pack, any reusable, versioned unit you can collect and deploy into a project.

Call that the <Term id="agentic-artifact">**agentic artifact**</Term>: whatever reusable, versionable unit shapes how the agent reasons, acts, accesses tools, applies context, follows policy, or produces work.

The runtime executes. A skill shapes its behavior. Markdown instructions don't reason on their own, and a signed context pack doesn't enforce the permissions it describes.

| Artifact family | Examples | What needs versioning and review |
| --- | --- | --- |
| Instruction | Prompts, skills, commands, rules | Non-executable instructions and any bundled executable dependencies |
| Tool | MCP servers, scripts, API adapters | Executable implementation, tool declarations, and permission boundaries |
| Context | Context packs, memories, domain references | Non-executable inputs, provenance, freshness, and scope |
| Governance | Policies, approvals, evaluation sets | Declared constraints and the mechanisms that enforce or test them |
| Execution | Workflows, agent definitions, deployment bindings | The configuration selecting instructions, tools, and runtime conditions |
| Evidence | Manifests, run records, verification results | Retained observations and their links to artifacts and accepted work |

Both executable code and non-executable context are versioned dependencies. Changing either can change runtime behavior. Freezing both makes the inputs inspectable; it doesn't freeze the model's reasoning.

A skill is small enough to install and large enough to carry intent. It can tell an agent how to perform a task, when to use supporting scripts, which references matter, and which constraints should shape execution. We're talking about more than just a prompt; it is a capability bundle.

## Follow the reviewer out of the registry

The lifecycle starts with **authoring**: the reviewer lives in one source repository, and a fix adds the missing guard. **Registration** makes that revision discoverable. **Approval** needs to attach to an exact revision and state its permitted use. The incident doesn't give me evidence of a complete approval record; it gives me a corrected source and a registry entry that didn't match deployment.

**Deployment** is where I lost the thread. A file copy is a separate object. Updating its source doesn't update it, and a successful registration says nothing about the copy another project loads.

The remedy is a recorded, registry-driven deployment. No hand copy. No symlink as a shortcut around the record. A symlink would follow the source checkout as branches changed, creating an unrecorded deployment that drifts with the branch instead of leaving stale bytes behind. Either way, “it's the same skill” conceals the state that matters.

At **use**, the project loads the deployed copy in its own context. The supply-chain obligation is to check that binding: the approved artifact, the expected context, and the allowed tools. The guard's presence is a prerequisite for the intended review, not evidence that the guard was followed.

At **drift**, declared and actual state separate. The fix stayed in the source repository while every project outside it kept loading the pre-fix reviewer. For five days, “fixed” described one location.

At **detection**, a gate compares deployed state with its source. The September 11 drift check classifies deployed entries, distinguishing tracked copies, justified copies, and drift; it also identifies symlinks. Drift fails the check.[^drift] A justified copy needs an explicit reason to differ. Otherwise exceptions become another way to lose the deployment record.

The next correction handles **missing dependencies**. An artifact absent locally is *unprovisioned, not non-existent*. The September 14 provisioning rule directs the agent back to the registry. Its failure hook suggests the deploy command; it doesn't write the artifact itself.[^provisioning] Hand-rolling a replacement would recreate the problem under a new name.

Keep this loose and fast locally. I want to experiment with a skill before promoting it, much as I can edit a branch before CI checks a shared change. The gates belong at promotion and use boundaries where another project starts depending on the result. Automate the comparison and make a failed check explain the repair. A meeting to approve every local prompt edit would solve a different problem: ensuring nobody uses the system.

Replacement and revocation also need a destination list. If I retire the reviewer, I need to find its deployed copies and prevent further use. Deleting the registry entry alone would leave those copies behind.

## A control fabric across many systems

“Control plane” is the familiar shorthand. But an enterprise will run many governance systems, with different owners and enforcement mechanisms. I use <Term id="control-fabric">**control fabric**</Term> for the shared identity, evidence, and explicit handoffs connecting four responsibilities:

| Responsibility | What it owes the reviewer workflow |
| --- | --- |
| **Supply chain** | Artifact identity, dependencies, recorded deployment, promotion, replacement, and revocation |
| **Runtime control** | Caller identity, current authorization, tool permissions, budgets, and enforcement during use |
| **Orchestration** | Routing the review, carrying its scope across handoffs, retries, and human decision points |
| **Evidence** | What ran, what it produced, what was verified, and who accepted it |

Shared identity means the deployment record and run record can refer to the same exact artifact. Shared evidence means the next system can inspect what the previous one established. An explicit handoff says who checks the next condition and what happens when it fails.

A configured integration is not enforcement; an advisory registration is not a gate.

## From deployed artifact to delivered outcome

**[Observed]** The lab receipts establish narrower facts: a stale reviewer copy, a drift detector, and related checks for instruction parity and stale operating guidance. They don't establish a complete artifact-version-to-outcome measurement system.

**[Proposed synthesis]** Closing that loop requires a run record that identifies which reviewer version was loaded, alongside the model, context, tools, and policy state. Join that record to the review's findings, verification, and acceptance decision. Then ask which runs used the old copy and which outputs need re-review. Where the loaded identity wasn't captured, mark the run's version unknown. Don't reconstruct certainty from the current registry.

Failure rate needs a denominator and a definition: failed reviews among comparable review tasks, with failure determined by an explicit acceptance criterion. A lower rate after deploying the guard would be useful evidence. It wouldn't isolate the guard's effect if the model or task mix changed too.

Drift can also happen against a frozen skill. Keep its bytes unchanged and change the runtime or context; the same instructions may produce different behavior. Compare those runs separately from an artifact-version change. Otherwise the registry gets blamed for degradation it didn't cause, or credit for an improvement it didn't produce.

The winning metric will be accepted outcomes with evidence, not activity. For this reviewer, that means a review that meets the request, with evidence of the required guard and an authorized acceptance decision. A <Term id="feature-contract">**Feature Contract**</Term> makes those obligations explicit; [The Contract Is the Work](/essays/the-contract-is-the-work/) takes up that boundary.

<Callout type="info" title="Four things that are not equivalent">
**Authenticity ≠ safety:** a known source can supply a harmful artifact.

**Authorization ≠ correctness:** permitted work can still be wrong.

**Traceability ≠ causal attribution:** a run using a skill doesn't establish that the skill caused its result.

**Pinned inputs ≠ determinism:** fixed dependencies don't make probabilistic reasoning deterministic.

*The Deterministic Envelope*, the planned, unpublished destination of this reading path, asks which surrounding controls can be deterministic and where fresh judgment still belongs.
</Callout>

## Where the system lied to us

**[Observed, September 11, 2026]** The drift-gate receipt records why the check was written: the deployed reviewer had spent five days without a mandatory guard. “The fix exists” had stood in for “the projects received the fix.” My own artifact-management workflow let that substitution pass.[^drift]

The related September 10 parity gate followed six weeks of stale doctrine reaching one class of agent harness. A harness is the software that loads instructions and runs the agent. Updating one harness-specific instruction file hadn't updated its sibling.[^parity] The staleness check from the same date searches live documents for assertions naming a superseded model as the operating “spine,” while exempting dated historical records.[^staleness]

These are detection mechanisms with different boundaries. Byte comparison catches the stale reviewer. Parity catches divergence between sibling instructions. The staleness check catches a particular outdated claim even when the files aren't supposed to be identical. But none proves that every remaining instruction is correct.

I call the umbrella **Agentic Systems Engineering**. Agentic SDLC is its application to software delivery. This reading path connects the questions; it isn't a one-to-one map of architecture layers.

The reviewer didn't need a better name or another catalog. It needed the fix to reach the place that loaded it, a check that noticed when it hadn't, and evidence that the resulting review did what was asked. That's the bar I want the supply chain to meet when I'm no longer watching every project myself.

## A discovery dies when the session closes.

The failure I keep designing against is small. A session makes a correct discovery, fixes something locally, and ends, and the discovery goes with it.

The fix survived, but the reason for it didn't.

The next agent repeats the reasoning, and the next reviewer has to reconstruct intent from the diff. Nothing crashed; my system just forgot. (That's a conceptual example, not a recorded incident, but it's the shape the failure keeps taking.)

<PullQuote variant="thesis-marker">The workflow state is outside the chat.</PullQuote>

What has to survive so the next person can continue?

[The AI Productivity Paradox](/essays/governed-agentic-sdlc-01-productivity-paradox/) asked why faster tasks don't always add up to faster delivery, and its answer kept landing on the same gap: no mechanism for one session's fix to survive into the next. This essay is about the operating model I documented to close that gap.

A single chat window gets asked to ideate, research, plan, execute, review, remember, and audit. The transcript feels productive while it's open. Then the assumptions vanish into scrollback, the next session starts from partial memory, and review has nothing stable to compare against.

That isn't a workflow. It's a storage bin with a conversation attached.

## The harder problem: the first artifact depends on the uncertainty.

Saving the discovery is the easy half. Write it down somewhere durable and the next session can at least find it.

The harder problem is that one place to write things down isn't enough, because different work needs a different first artifact. A research question, a half-formed product idea, and an already-planned phase each lose something different when the session closes.

The better question isn't "which model is best?" Rather, it's this: **what is the first artifact this task needs to become legible?** Once that artifact exists, the rest of the workflow has something to inherit.

I've started thinking about AI work less as a tool choice and more as a routing problem.

The common pattern is to start with a preferred interface: ChatGPT, Claude, Gemini, Perplexity, Codex, NotebookLM, whatever happens to be open. That feels efficient because there's no ceremony, but it also hides the most important decision: what shape should this work take before any agent starts expanding it?

For me, the first pass usually comes down to five lenses:

| Lens | Question |
| --- | --- |
| Sensitivity | Is the work public-safe, internal-sensitive, proprietary, or regulated? |
| First artifact | Does the task need a PRD, storyboard, research memo, progress file, evidence bundle, or something else? |
| Speed versus depth | Is this a fast first pass, decision-grade research, or multi-agent execution? |
| Cost | Is a subscription UI enough, or does the task justify metered API or swarm execution? |
| Reusability | Is this a one-off answer, or should the output become a repeatable pipeline? |

The important move is routing to the system strongest at producing the first durable artifact, not the final deliverable. A research question may start in a search-heavy tool because the first artifact is a memo. A software idea may start as voice notes, move into a PRD, then into a local coding agent. A deck may start as a text storyboard before any image generation happens.

The final output matters, but without the first artifact, every step after it is guessing.

## Intent becomes durable state.

Go back to the opening session. Its transcript held the discovery right up until the session ended, which is the trouble: a transcript is useful as an interaction surface, but it's a terrible source of truth.

It has no native notion of ownership, dependency, review intensity, or completion evidence. A rule can be mentioned in the scrollback, but the transcript doesn't carry it as state that routes the next agent: that a feasibility question should stop before implementation, or that a high-risk migration should trigger a hard boundary before edits. It can't separate the facts worth reusing from the scaffolding of one run, which is exactly the line the lost discovery needed someone to draw.

Now picture what the session could have written instead: exploration charters, feasibility briefs, feature contracts, PRDs, implementation plans, decision blocks, progress files, validation records, run evidence, and knowledge handoffs. In the June model I documented, those make up the <Term id="artifact-graph">**artifact graph**</Term>, the opposite of the transcript: a typed set of durable objects that the workflow can resume from and reviewers can validate against.

That can sound like process overhead until you watch the alternative happen a few times. The session we started with is that alternative, and it has one more cost I haven't named yet: the next planning pass can't tell what was deferred from what was deliberately rejected.

It's an operating-state failure, not a model failure.

### Triage before commitment

The first orchestration question isn't "which files should I edit?" Rather, it's "what kind of uncertainty is this?"

That distinction matters because different uncertainty needs different artifacts. An ambiguous product idea needs exploration. A technical feasibility question needs a SPIKE. A known feature needs tier classification and a <Term id="feature-contract">Feature Contract</Term> or PRD. An already-planned phase needs execution from progress state, not another round of brainstorming.

In the storyboard behind this post, the flow is explicit:

| Situation | Preferred path | First durable output |
| --- | --- | --- |
| Ambiguous idea or risky direction | `/plan:explore` | Exploration Charter |
| Research-heavy feasibility question | `/plan:spike` | FeasibilityBrief |
| Known feature needing planning | `/plan:plan-feature` | Feature Contract or PRD |
| Already planned phase execution | `/dev:execute-phase` | Updated progress and evidence |

In that routing, exploration is not a side quest. It's a gate: it's meant to let the system reduce uncertainty before it commits to a contract, a PRD, or an execution graph.

### Artifacts operate the work

I don't treat these artifacts as documentation in the usual sense. Documentation explains work after the fact; these artifacts operate the work while it's happening.

A FeasibilityBrief captures whether a path is viable and with what confidence. A Feature Contract gives a bounded autonomous sprint enough structure to execute. A Progress File records the run state. The names matter less than the jobs, though, and each artifact has one:

| Artifact | Job |
| --- | --- |
| Exploration Charter | Reduce ambiguity before commitment. |
| FeasibilityBrief | Turn research into a go, conditional-go, or no-go decision. |
| Feature Contract | Give Tier 1 work a compact execution handoff. |
| PRD | Preserve product and behavioral intent. |
| Implementation Plan | Sequence phases, tasks, dependencies, and verification. |
| Progress File | Store current execution state and evidence. |

Put the lost discovery back into that table and the failure gets specific. Its run state never reached a Progress File, so the next session couldn't see it, and its reasoning never reached a plan or PRD, so the reviewer had only the diff.

This is where AI workflows start to compound. The next session doesn't need to infer what the previous one discovered. The reviewer doesn't need to guess which acceptance criteria mattered, and the orchestrator doesn't need to hold every dependency in chat context. That's the design intent, not a measured gain.

The workflow state is outside the chat. That's the whole point.

## Risk determines the graph and its review.

A typo fix, a UI polish pass, an API contract migration, a permission boundary, and a production database change don't deserve the same autonomy.

Autonomy isn't binary; it's progressive. Small, clear work shouldn't require a 20-page plan, and risky work shouldn't get the same autonomy as a copy edit. The operating model needs to move fast where the blast radius is low and slow down where uncertainty, file movement, data risk, or core-path changes make mistakes expensive.

The tiering model I documented in June is intentionally simple:

| Tier | Typical shape | Planning artifact | Review gate |
| --- | --- | --- | --- |
| Tier 0 | Tiny safe change | Inline plan or small progress note | Optional reviewer |
| Tier 1 | Bounded feature | Feature Contract | Mandatory <Term id="task-completion-validator">validator</Term> |
| Tier 2 | Coordinated work | PRD plus Implementation Plan | Per-phase validation |
| Tier 3 | High-risk work | SPIKE, PRD, plan, milestone gates | Higher-risk reviewer or council |

The table is the documented mapping, not a log: it says which review each tier calls for, and this essay doesn't show a real classification or reviewer invocation.

This is also why I don't like "autonomous agent" as a blanket phrase.

### Execution is a graph

For Tier 2 and Tier 3 work, a linear task list isn't enough.

The shape the June model specifies is an <Term id="executiongraph">**ExecutionGraph**</Term>, and it's deliberately boring. It's meant to give the orchestrator a way to parallelize without pretending all work is independent. Waves serialize major dependency boundaries, and the phases inside a wave can run in parallel when it's safe. Batches keep file ownership from colliding. Tasks map to bounded agents and review expectations.

<details>
<summary>Inside my lab: the ExecutionGraph shape</summary>

```text
ExecutionGraph
  waves[] sequential by dependency
    phases[] potentially parallel
      batches[] grouped by file ownership and dependency safety
        tasks[] assigned to agents with model/provider hints
```

</details>

This matters because "use more agents" isn't a strategy. Parallelism without ownership rules creates cleanup work. The execution graph is how I get useful parallelism without turning the main thread into a merge-conflict coordinator, though this essay shows the design, not a collision test.

When a task in that graph leans on a reusable agent or skill (the validator in the tier table is one), the graph is assuming that capability is still what it was when the task was planned. Keeping that assumption true across projects is a problem for the next essay.

## Review has distinct boundaries.

A validator checking a Tier 1 feature and a review council looking at a production migration both get called review, but they aren't the same action.

Review isn't a vibe.

The system has to know whether it's doing normal validation, higher-risk validation, adversarial review, or a hard stop before edits. Those are different actions with different permissions.

In the storyboard, review intensity is a routing field:

| Review intensity | Typical reviewer | Use when |
| --- | --- | --- |
| `standard` | `task-completion-validator` | Normal Tier 1 or Tier 2 validation. |
| `tier3` | Higher-risk validator | High-risk phase, milestone, or broad behavior change. |
| `council` | Review council | Auth, payments, deletion, API contracts, migrations, core paths. |

<Term id="mode-d">Mode D</Term> is the one worth calling out because it's easy to get wrong. Mode D isn't "be careful." It's a brake: in the June model, the workflow is meant to stop before edits when the work crosses a high-risk boundary and needs explicit signoff.

That may feel slower. It's supposed to.

For auth, payments, destructive deletion, secret rotation, production migration, and core infrastructure changes, the safer move is to stop the workflow before edits. Asking an implementation agent to "be careful" isn't the same control. But that recommendation doesn't establish an enforced stop, either: it says where the brake belongs, not that it fires.

## Evidence and cost are part of the deliverable.

The lost discovery left a code change behind, and nothing else.

The work isn't done when code changes. It's done when the system can explain what happened, why it happened, what passed, what failed, what remains, and what should be reusable. That's why progress and evidence aren't cleanup. Rather, they're the product of the run.

For my workflows, the evidence stack I documented in June looks like this:

| Layer | What it preserves |
| --- | --- |
| Progress state | Task status, dependency state, blockers, current phase. |
| Validation record | Checks, build output, review notes, acceptance criteria. |
| Run intelligence | Session traces, failures, ownership, time, evidence links. |
| Human capsule | Readable summary for stakeholders and future operators. |
| Knowledge surface | Decisions, reusable patterns, deferred items, source links. |

That's where adjacent systems become interesting. Not because every post needs to explain each one, but because they're surfaces for the same operating-state problem: how do you make agent work inspectable, reusable, and recoverable after the session ends?

<Term id="ccdash">CCDash</Term> is a dashboard for inspecting agent sessions and workflow outcomes. <Term id="meatywiki">MeatyWiki</Term> is a durable knowledge store built on a markdown vault, and <Term id="intenttree">IntentTree</Term> is the task graph that tracks intents, dependencies, and completion state. HTML Capsules are readable summaries for stakeholders, and <Term id="skillmeat">SkillMeat</Term> is my registry for reusable agent capabilities. I'm not claiming they cover that stack evenly, and this essay doesn't measure which layers actually get written.

### Tool choice follows the artifact

A deck that starts as a text storyboard doesn't need an image tool yet; it needs the narrative locked first. Tool choice still matters, but it comes later than most people think.

The practical rule is to choose the tool that best produces the first artifact:

| Workflow | First artifact | Typical shape |
| --- | --- | --- |
| Research | Research memo or source packet | Orchestrate the question, run the search, retain the corpus. |
| Software planning | PRD or feature contract | Move from raw idea to scoped artifact before implementation. |
| Presentations | Text storyboard | Lock narrative before generating visual scaffolds. |
| Cost governance | Routing decision | Start with low marginal cost, escalate only when value is explicit. |

Specific tools change, but the roles are more durable.

That's why I try to avoid tool-first language even when I'm talking about tools I use constantly. The point isn't that a particular product is always the answer. Rather, it's that research, planning, execution, review, and retention are different jobs, and collapsing them into one chat window makes every tool look worse than it is.

### Cost is a gate too

If a subscription UI can produce the first artifact at the required fidelity, I use that. If exact parameters, repeatability, visual control, or multi-agent analysis actually matter, then I escalate.

Metered automation is not maturity by itself. A swarm is justified when the extra rigor, repeatability, or parallel execution changes the outcome, not because the task feels more serious when more agents are involved.

This is one of the reasons artifact-first routing helps: it forces the cost question into the open. What are we buying with the escalation? Faster exploration? Better verification? Reusable output? Stronger visual fidelity? If the answer is vague, the workflow is probably using cost to avoid making a routing decision.

## A graph can compound only what it retains.

Run the opening session through the graph one more time. It's meant to keep the discovery, the intent behind the fix, and whatever verification evidence exists, but keeping them isn't the same as being right about them.

A transcript decays; a graph compounds. The graph is meant to make human intent reviewable, agent execution resumable, and evidence part of the deliverable rather than a screenshot pasted into a status update.

The operating system isn't the model stack. Rather, it's the artifact path: intake, route, draft, execute, review, persist. Once that path exists, better models help, but without it they mostly produce faster decay.

<WhereThisSits slug="agentic-operations-flow" />

I place this essay within <Term id="agentic-systems-engineering">Agentic Systems Engineering</Term>, a discipline already named in academic and enterprise work.[^ase] My <Term id="aos">Agentic OS (AOS)</Term> is the personal lab context for this documented operating model.

The session that found the fix didn't need a better model or a longer transcript. It needed its discovery written where the next agent would look first. It needed its intent recorded before the diff had to speak for it, and evidence a reviewer could check without reconstructing the run. It also needed the right first artifact for the uncertainty it hit, which no amount of saving solves. That's the bar I want the graph to meet when I'm not the one opening the next session.

But a graph leans on reusable pieces: the validator, the agents, the skills each task lands on. Whether those are still what the graph thinks they are, after they've been copied, deployed, and changed for good local reasons, is where [The Registry Wave Is Here](/essays/the-registry-wave-agentic-artifact-supply-chain/) picks up.

Most AI work does not fail because the model was too weak. It fails earlier, at the moment the work gets routed.

A single chat window gets asked to ideate, research, plan, execute, review, remember, and audit. The transcript feels productive while it is open. Then the assumptions vanish into scrollback, the next session starts from partial memory, and review has nothing stable to compare against.

That is not a workflow. It is a storage bin with a conversation attached.

The better question is not "which model is best?" It is: **what is the first artifact this task needs to become legible?** Once that artifact exists, the rest of the workflow has something to inherit.

## Route to the First Artifact

I have started thinking about AI work less as a tool choice and more as a routing problem.

The common pattern is to start with a preferred interface: ChatGPT, Claude, Gemini, Perplexity, Codex, NotebookLM, whatever happens to be open. That feels efficient because there is no ceremony. It also hides the most important decision: what shape should this work take before any agent starts expanding it?

For me, the first pass usually comes down to five lenses:

| Lens | Question |
| --- | --- |
| Sensitivity | Is the work public-safe, internal-sensitive, proprietary, or regulated? |
| First artifact | Does the task need a PRD, storyboard, research memo, progress file, evidence bundle, or something else? |
| Speed versus depth | Is this a fast first pass, decision-grade research, or multi-agent execution? |
| Cost | Is a subscription UI enough, or does the task justify metered API or swarm execution? |
| Reusability | Is this a one-off answer, or should the output become a repeatable pipeline? |

The important move is routing to the system strongest at producing the first durable artifact, not the final deliverable. A research question may start in a search-heavy tool because the first artifact is a memo. A software idea may start as voice notes, move into a PRD, then into a local coding agent. A deck may start as a text storyboard before any image generation happens.

The final output matters. But without the first artifact, every step after it is guessing.

## Chat Is the Wrong Container

The transcript is useful as an interaction surface. It is a terrible source of truth.

It has no native notion of ownership, dependency, review intensity, or completion evidence. It does not know that a feasibility question should stop before implementation. It does not know that a high-risk migration should trigger a hard boundary before edits. It does not know which facts should become reusable context and which are just scaffolding from the current run.

The <Term id="artifact-graph">**artifact graph**</Term> is the opposite: a typed set of durable objects that the workflow can resume from and reviewers can validate against. In my current system, that graph includes exploration charters, feasibility briefs, feature contracts, PRDs, implementation plans, decision blocks, progress files, validation records, run evidence, and knowledge handoffs.

That can sound like process overhead until you watch the alternative happen a few times. A session makes a correct discovery, fixes something locally, and then the discovery dies when the session closes. The next agent repeats the same reasoning. The next reviewer has to reconstruct intent from diff shape. The next planning pass cannot tell what was deferred and what was deliberately rejected.

Not a model failure. An operating-state failure.

## Triage Before Commitment

The first orchestration question is not "which files should I edit?"

It is "what kind of uncertainty is this?"

That distinction matters because different uncertainty needs different artifacts. An ambiguous product idea needs exploration. A technical feasibility question needs a SPIKE. A known feature needs tier classification and a contract or PRD. An already-planned phase needs execution from progress state, not another round of brainstorming.

In the storyboard behind this post, the flow is explicit:

| Situation | Preferred path | First durable output |
| --- | --- | --- |
| Ambiguous idea or risky direction | `/plan:explore` | Exploration Charter |
| Research-heavy feasibility question | `/plan:spike` | FeasibilityBrief |
| Known feature needing planning | `/plan:plan-feature` | Feature Contract or PRD |
| Already planned phase execution | `/dev:execute-phase` | Updated progress and evidence |

Exploration is not a side quest. It is a gate. It lets the system reduce uncertainty before it commits to a contract, a PRD, or an execution graph.

## Artifacts Are Operating State

I do not treat these artifacts as documentation in the usual sense. Documentation explains work after the fact. These artifacts operate the work while it is happening.

An Exploration Charter frames what needs to be learned. A FeasibilityBrief captures whether a path is viable and with what confidence. A Feature Contract gives a bounded autonomous sprint enough structure to execute. A PRD describes behavior and intent. An Implementation Plan turns that intent into phases, dependencies, and gates. A Progress File records the run state.

The important part is not the names. The important part is that each artifact has a job:

| Artifact | Job |
| --- | --- |
| Exploration Charter | Reduce ambiguity before commitment. |
| FeasibilityBrief | Turn research into a go, conditional-go, or no-go decision. |
| Feature Contract | Give Tier 1 work a compact execution handoff. |
| PRD | Preserve product and behavioral intent. |
| Implementation Plan | Sequence phases, tasks, dependencies, and verification. |
| Progress File | Store current execution state and evidence. |

This is where AI workflows start to compound. The next session does not need to infer what the previous one discovered. The reviewer does not need to guess which acceptance criteria mattered. The orchestrator does not need to hold every dependency in chat context.

The workflow state is outside the chat. That is the whole point.

## Autonomy Scales With Risk

Autonomy is not binary. It is progressive.

Small, clear work should not require a 20-page plan. Risky work should not get the same autonomy as a copy edit. The operating model needs to move fast where the blast radius is low and slow down where uncertainty, file movement, data risk, or core-path changes make mistakes expensive.

The tiering model I use is intentionally simple:

| Tier | Typical shape | Planning artifact | Review gate |
| --- | --- | --- | --- |
| Tier 0 | Tiny safe change | Inline plan or small progress note | Optional reviewer |
| Tier 1 | Bounded feature | Feature Contract | Mandatory validator |
| Tier 2 | Coordinated work | PRD plus Implementation Plan | Per-phase validation |
| Tier 3 | High-risk work | SPIKE, PRD, plan, milestone gates | Higher-risk reviewer or council |

This is also why I do not like "autonomous agent" as a blanket phrase. Autonomous relative to what? A typo fix, a UI polish pass, an API contract migration, a permission boundary, and a production database change do not deserve the same autonomy.

## Execution Is a Graph

For Tier 2 and Tier 3 work, a linear task list is not enough.

The shape I use is an <Term id="executiongraph">**ExecutionGraph**</Term>:

```text
ExecutionGraph
  waves[] sequential by dependency
    phases[] potentially parallel
      batches[] grouped by file ownership and dependency safety
        tasks[] assigned to agents with model/provider hints
```

That structure is deliberately boring. It gives the orchestrator a way to parallelize without pretending all work is independent. Waves serialize major dependency boundaries. Phases can run in parallel when safe. Batches keep file ownership from colliding. Tasks map to bounded agents and review expectations.

This matters because "use more agents" is not a strategy. Parallelism without ownership rules creates cleanup work. The execution graph is how I get useful parallelism without turning the main thread into a merge-conflict coordinator.

## Gates Are Typed

Review is not a vibe.

The system has to know whether it is doing normal validation, higher-risk validation, adversarial review, or a hard stop before edits. Those are different actions with different permissions.

In the storyboard, review intensity is a routing field:

| Review intensity | Typical reviewer | Use when |
| --- | --- | --- |
| `standard` | `task-completion-validator` | Normal Tier 1 or Tier 2 validation. |
| `tier3` | Higher-risk validator | High-risk phase, milestone, or broad behavior change. |
| `council` | Review council | Auth, payments, deletion, API contracts, migrations, core paths. |

Mode D is the one worth calling out because it is easy to get wrong. Mode D is not "be careful." It is a brake. The workflow stops before edits when the work crosses a high-risk boundary and needs explicit signoff.

That may feel slower. It is supposed to.

<Callout type="warning" title="A hard boundary is not a prompt style">
For auth, payments, destructive deletion, secret rotation, production migration, and core infrastructure changes, the safer move is to stop the workflow before edits. Asking an implementation agent to "be careful" is not the same control.
</Callout>

## Evidence Is Part of the Deliverable

The work is not done when code changes.

It is done when the system can explain what happened, why it happened, what passed, what failed, what remains, and what should be reusable. That is why progress and evidence are not cleanup. They are the product of the run.

For my workflows, the evidence stack looks like this:

| Layer | What it preserves |
| --- | --- |
| Progress state | Task status, dependency state, blockers, current phase. |
| Validation record | Checks, build output, review notes, acceptance criteria. |
| Run intelligence | Session traces, failures, ownership, time, evidence links. |
| Human capsule | Readable summary for stakeholders and future operators. |
| Knowledge surface | Decisions, reusable patterns, deferred items, source links. |

That is where adjacent systems such as CCDash, MeatyWiki, IntentTree, HTML Capsules, and SkillMeat become interesting. Not because every post needs to explain each one. Because they are surfaces for the same operating-state problem: how do you make agent work inspectable, reusable, and recoverable after the session ends?

## Where Tool Choice Actually Matters

Tool choice still matters. It just comes later than most people think.

The practical rule is to choose the tool that best produces the first artifact:

| Workflow | First artifact | Typical shape |
| --- | --- | --- |
| Research | Research memo or source packet | Orchestrate the question, run the search, retain the corpus. |
| Software planning | PRD or feature contract | Move from raw idea to scoped artifact before implementation. |
| Presentations | Text storyboard | Lock narrative before generating visual scaffolds. |
| Cost governance | Routing decision | Start with low marginal cost, escalate only when value is explicit. |

Specific tools change. The roles are more durable.

That is why I try to avoid tool-first language even when I am talking about tools I use constantly. The point is not that a particular product is always the answer. The point is that research, planning, execution, review, and retention are different jobs. Collapsing them into one chat window makes every tool look worse than it is.

## Cost Is a Gate Too

Metered automation is not maturity by itself.

A swarm is justified when the extra rigor, repeatability, or parallel execution changes the outcome. It is not justified because the task feels more serious when more agents are involved. If a subscription UI can produce the first artifact at the required fidelity, I use that. If exact parameters, repeatability, visual control, or multi-agent analysis actually matter, then I escalate.

This is one of the reasons artifact-first routing helps. It forces the cost question into the open. What are we buying with the escalation? Faster exploration? Better verification? Reusable output? Stronger visual fidelity? If the answer is vague, the workflow is probably using cost to avoid making a routing decision.

## The System Compounds

A transcript decays. A graph compounds.

That is the simplest version of the argument. A transcript can be useful during the moment of work, but it is weak operating state. It does not naturally preserve decisions, dependencies, artifacts, review intensity, evidence, or reusable knowledge.

An artifact graph does. It lets human intent become reviewable, agent execution become resumable, and evidence become part of the deliverable rather than a screenshot pasted into a status update.

The operating system is not the model stack. It is the artifact path: intake, route, draft, execute, review, persist. Once that path exists, better models help. Without it, better models mostly produce faster decay.

The plan for the shipped-work-ledger opened with a wrong assumption, and it opened that way on
purpose: better to find out on day one that a skill the plan called "net-new" already existed,
just undeployed, than to spend a milestone rebuilding it from scratch.

## What we set out to do

Give the Agentic OS one trustworthy answer to "what shipped," across four milestones: a linter that
enforces a single canonical status vocabulary across the whole plan corpus (M1); a mechanism that
binds IntentTree tracker nodes to the plan files and feature slugs they represent, in both
directions (M2); a query that proves what actually shipped, with real commit and PR evidence
attached, not an inferred guess (M3); and a folder-layout simplification plus an authoring-time gate
so the whole structure doesn't drift again (M4).

## What happened

M1 started by correcting its own premise: the "missing" skill was real and rich, just never
deployed locally, so the milestone became "deploy and add the one genuinely missing script," not a
rebuild. It landed a linter that normalized 128 files across the corpus to a single valid status
vocabulary, plus a `planning_maturity` field, byte-preserving and additive.

M2 built the node-side and file-side stamping that connects a tracker node to the plan file it
represents. The first real defect showed up immediately: the CLI's own metadata-write path silently
turned nested data into flattened text on write, a genuine corruption risk for the exact nodes the
milestone needed to touch. The write path moved to a verified HTTP call instead, and a second defect
surfaced right behind it: one of the "slugs" the resolver was about to stamp turned out to be
leftover residue from a bad import, not a real feature at all. A shape guard closed that gap before
anything got written. Two more resolution paths (a tag-based match, and a fallback file reference)
closed the remaining acceptance criterion.

M3 built the evidence layer across four parallel legs, and every one of the milestone's real defects
followed the same shape: invisible to a fully green offline test suite, and only visible once the
code ran against live data. A field name the write path used didn't match the field the read path
actually returned. Evidence was landing on the wrong node in a shared subtree. A repo-inference
routine that looked fixed on the first pass was silently wrong on the second. And a citation that
looked shape-valid (a plausible-looking commit reference) pointed at a commit that didn't exist. Each
was found, fixed, and covered with a regression test pinned to the real shape, not the assumed one.
The milestone closed on an honest number: six of eight features with a resolvable evidence link
carry one, and twenty-six of thirty-four completed nodes in this repo have no join key at all,
because the underlying data has nothing to join on, not because the logic is too strict.

M4 carried the most risk: an authoring-time advisory gate, a stamp applied at node-creation time so
the gap M3 measured stops reopening, and a corpus-wide folder move touching hundreds of files and
their cross-references. Its own thirty-nine-test suite was green and still missed three real
defects, all caught only by running the tool against the real repository: an unhandled edge case
that aborted a migration mid-run, a phase that gave different answers depending on the order it ran
in, and a class of relative links inside the moved files themselves that nothing had been checking.
The orchestrator also caught a fourth problem the plan hadn't scoped at all: dozens of authoring
templates across the skill docs still pointed at the old folder layout, which would have silently
rebuilt the very structure this milestone just removed. One process failure happened along the way:
a `git reset --hard` was run on the assumption an earlier commit had already succeeded, discarding
four legs of work in one command. It was recovered in full, byte for byte, from git's own
dangling-object store.

## Wins

- A single canonical status vocabulary is now enforced across the plan corpus, continuously, not as
  a one-time cleanup.
- Node-to-plan and plan-to-node binding both work, verified live on real trees in two repositories,
  with zero metadata lost or silently retyped along the way.
- A real "what shipped" query exists, with evidence traced to actual commits and pull requests, not
  inferred or fuzzy-matched.
- The folder simplification landed with every reference accounted for: zero unexplained skips, zero
  dangling links left unexplained.
- A discarded commit was recovered in full from git internals rather than lost.

## Losses

- Coverage is honestly partial. Twenty-six of thirty-four completed nodes in this repo carry no
  feature identity at all, and no amount of heuristic matching invents a join key that doesn't
  exist in the underlying data.
- Nearly every real defect across all four milestones was invisible to a green, fully passing
  offline test suite, and only surfaced once the code ran against a live server or a real
  repository. That pattern repeated often enough to name: a test double that is more permissive
  than the thing it stands in for will certify broken behavior as correct.
- One avoidable process failure: a destructive git operation was run without confirming the
  operation before it had actually succeeded.

## What it changed (meta-findings)

The recurring lesson across every milestone was the same lesson in a new costume: a green offline
suite proves the code matches a model of its dependency, not the dependency itself. Every serious
defect in this program (the metadata write path, the evidence field mismatch, the CLI flag
ordering elsewhere in this same family of work, the folder-move ordering bug) was caught only by
running the real thing, never by the tests written in advance of running it. A second, related
lesson: "shape-valid" and "real" are different claims, worth checking separately (a plausible commit
reference, a plausible feature slug, a plausible node id can all be wrong in ways that only a live
check catches). And a third, procedural one: never run a destructive command on the assumption a
prior command already succeeded; check that the state actually moved.

## How it fits the AOS arc

This closes a structural gap the Agentic OS has needed for a while: a queryable, evidence-backed
answer to what actually shipped, joining the task graph to the plan corpus to real git history,
instead of requiring a human to reconstruct that story by hand after the fact. It also reinforces a
lesson this family of programs keeps re-learning in different shapes (the same "fake stood in for a
live dependency and both looked fine until the real thing ran" failure appears again in a sibling
delivery program run around the same time). The structural fix each time is the same: stamp
identity at the moment something is created, not as a backfill later, so the next ledger query
doesn't inherit the same gap.

### M2 correction — CLI `--meta` write path rejected; moved to a verified HTTP PATCH seam (2026-07-31)

The conservative "report, don't route around" call above was revisited and reversed after
measuring the actual blast radius, rather than staying a documented-but-live risk on real shared
state: **38 of this tree's 143 nodes carry a nested `meta` value** (`fingerprint`, `outcome`,
`commit_refs`, `related_documents`), a meaningful share of them already `completed` — i.e. exactly
the nodes M2's acceptance criterion targets for stamping. Since `itt node update --meta` can only
express a bare float or a raw string per value, every read-merge-write through that seam would
silently coerce those dicts/lists into JSON-text strings on write. That is not an acceptable
production write path for a tool whose whole job is joining live shared state — a reviewed risk
note next to a real corruption path is still a real corruption path.

**Fix:** `_itt_client.IttClient.update_node_meta` now writes via a raw HTTP `PATCH
http://<api_url>/api/v1/nodes/{node_id}` with body `{"meta": <full merged dict>}` — a real JSON
object, so nested values keep their type. This was verified directly against the **live** node
server before landing: round-tripping the ledger node's real `meta` (including its `fingerprint`
dict) through this endpoint returned a byte-identical dict, still typed as an object. Confirmed
`/api/v2/nodes/...` is 404 for this resource — `/api/v1` is correct. `api_url`/`api_token`
resolution mirrors the `itt` CLI's own precedence exactly (explicit arg > `INTENTTREE_API_URL` /
`INTENTTREE_API_TOKEN` env > `~/.config/intenttree/config.toml` keys `api_url`/`api_token`); the
token is never logged. **Reads stay on the existing `itt --json` CLI seam** (`tree graph`, `sync
status`, `node get`) — only the write moved; the module docstring calls out the two-transport
split explicitly so it doesn't get "fixed" back into one. The implementation uses stdlib
`urllib.request` only (no new dependency), and both the CLI `runner` and the new `http_call` are
independently injectable, so the test suite stays fully offline — no socket is ever opened by
`pytest`.

The old `_meta_cli_value` JSON-stringify workaround and its pinning test
(`test_update_node_meta_serializes_nested_values_as_json_string`) are removed; replaced with
type-preservation tests (`test_update_node_meta_patch_body_preserves_nested_types`,
`test_apply_patch_body_preserves_nested_meta_as_object`) plus config/env/token-resolution tests
(`test_resolve_api_url_precedence_env_over_config_file`, `test_resolve_api_url_falls_back_to_config_file`,
`test_resolve_api_token_from_config_file`, `test_resolve_api_token_explicit_arg_wins`,
`test_token_never_appears_in_url_or_is_hardcoded`).

**Follow-up logged, not fixed here:** the CLI's `--meta KEY=VALUE` parser having no JSON-object
mode is a genuine product gap in `../intenttree` (`intenttree_client/cli/commands/node_cmd.py`'s
`_parse_kv_option`) — worth an upstream fix (e.g. a `--meta-json` flag or JSON-sniffing the
value) so other CLI consumers don't hit the same silent type-coercion trap. Not addressed in this
program; this tool works around it at the client-library layer instead.

### M2 correction — slug-shape guard added; one node in the dry-run was ID-shaped residue, not a real slug (2026-07-31)

Reviewing the dry-run output (60 stamps across 3 slugs) surfaced a defect: one of the three
"slugs" the resolver produced, `srcart_01KXHQR6F69Y80GX1B6VF4FZFB`, is not a feature slug at
all — it is a source-artifact id. Its origin: the affected work_package node (type
`work_package`, `meta.origin: "imported_plan"`) has its `title` field literally set to the
string `"srcart_01KXHQR6F69Y80GX1B6VF4FZFB"`. This is residue from an earlier bad import: some
plan file carried no `feature_slug` in its frontmatter, and whatever ran the import fell back to
the artifact id for both the node's title and the sync-bindings `source_task_id:
"feature:<id>"` entry — so the M2 `retroactive_binding` resolution path (bindings alone, no
plan file needed) faithfully resolved exactly what the bindings table said, and what the
bindings table said was itself corrupt. Stamping it would have written a fake feature into the
ledger — worse than leaving the node unstamped, since a downstream "what shipped" query would
then surface a nonsense feature as if it were real delivered work. Exactly the "a wrong join
poisons trust" risk the plan calls out.

**The fix — a slug-shape guard in the resolution layer, not just the retroactive path.** Added
`slug_shape_reject_reason()` / `is_slug_shaped()` to `_slug_resolution.py`, applied inside
`resolve_candidates()`'s `_set()` helper so it runs on every resolution attempt from all three
paths ((a) `direct`, (b) `source_artifact`, (c) `retroactive_binding`) — any path can be poisoned
by the same kind of degenerate-import residue, not only the retroactive one. The rule is a
positive shape test first (a real feature slug is lowercase kebab-case: `^[a-z0-9]+(-[a-z0-9]+)*$`,
no underscores, no uppercase), with explicit belt-and-braces rejects for: a bare ULID-looking
token (long uppercase-alnum run, no hyphens), a known AOS entity-id prefix
(`srcart_`/`node_`/`tree_`/`ws_`/`bind_`/`agt_`/`actor_`/`run_`/`sess_`/`exec_`/`wf_`/`task_`/
`atlas_`/`intent_`/`ds_`), and a *generic* `^[a-z]{2,12}_[0-9A-Za-z]{6,}$` pattern specifically so
an unanticipated new `xxx_01...`-shaped prefix is still caught even if nobody adds it to the
explicit list. `resolve_candidates()` now returns `(candidates, rejected)` — a rejected value is
never added to `candidates` and therefore can never be stamped, regardless of what any other path
resolves for that node. `stamp-node-slug.py` reports it in its own `rejected_slug_shape` summary
bucket (node_id + offending value + reason), separate from `conflicts`, but **the run still exits
2** — my call, matching the operator's: an ID-shaped resolved slug is a data-quality defect a
human needs to see, so it is treated like a conflict for exit-code purposes, but counted
separately so the two causes (write conflicts vs. shape rejects) stay distinguishable in the
report. `verify-slug-roundtrip.py` runs the same `slug_shape_reject_reason()` check on every
node's live `meta.feature_slug` before doing any other check, so a round-trip against an
ID-shaped value reports FAIL-with-reason rather than a spurious PASS (defensive — covers the case
where such a value somehow got live on a node by some other path).

Tests added to `tests/test_stamp_node_slug.py`: a new `TestSlugShapeGuard` class covering the
exact `srcart_01KXHQR6F69Y80GX1B6VF4FZFB` case, several other id-prefixed values plus an
unanticipated-prefix case (`xyzid_01...`, proving the generic regex catches it), bare-ULID
values, and several legitimate hyphenated slugs passing cleanly (including a single-word slug);
a new fixture node (`node_G`) whose only resolution is retroactive-binding-to-an-artifact-id,
proving it never becomes a stamp candidate and is left with untouched `meta == {}` even under
`--apply`; and a `verify-slug-roundtrip` case proving an ID-shaped stamped slug fails with a
reason rather than passing. Full suite: `python3 -m pytest
.claude/skills/artifact-tracking/scripts/tests/` → **128 passed**.

Re-ran the dry-run against `tree_01KVTH95ETM8YRYCV2ENHVR124` (still no `--apply`, no git):
`nodes_scanned=143`, `resolvable=60` (was 61 — the srcart node moved out of `candidates`),
`unresolvable=82`, `would_stamp=59` (was 60), `already_correct=1`, `conflicts=0`,
**`rejected_slug_shape=1`** (new bucket), `applied=0`. Process exit code confirmed **2** (rejected
now drives the same non-zero exit as a conflict would). This matches the operator's expectation
exactly (`would_stamp=59`, `rejected_slug_shape=1`).

**Out of scope, logged for a separate cleanup:** that same work_package node is pre-existing
bad-import residue in the live tree — its title is literally the source-artifact id string and it

### M2 — three closing gaps: `tag_match`, `plan_ref` backfill, file-side `stamp-plan-binding.py` (2026-07-31)

The first M2 pass proved the write seam and shipped a working node-stamper, but a live
`--apply` run (59 nodes stamped, 0 meta keys lost, 0 type changes, all 118 nested values
preserved — the HTTP PATCH seam verified good in production) surfaced the actual shape of the M2
acceptance criterion: **all 59 stamped nodes are `not_started`** (imported plan artifacts), while
**0 of the 32 `completed` nodes** — exactly what a "what shipped" query returns — carried
`feature_slug`. The completed nodes are hand-created, never ran through a sync import, and so
never had a chance at paths (a)/(b)/(c); they carry the feature identity only in their own `tags`.
Three gaps closed this off.

**Gap 1 — `tag_match`, a fourth resolution path (`_slug_resolution.resolve_tag_match_candidates`).**
Lowest precedence — only attempted for a node with NO resolution at all from (a) direct / (b)
source_artifact / (c) retroactive_binding (`already_resolved` param excludes them entirely; the
path never gets a chance to override a higher-precedence hit, and per the M2 correctness lesson
from `_slug_resolution`'s own history, a node that was merely *rejected* by the shape guard on an
earlier path IS still eligible here — a poisoned retroactive binding shouldn't permanently block a
legitimate tag-based recovery for the same node). The match itself is deliberately narrow: **exact
string equality only** between a node's `tags` entries and the set of `feature_slug` values
actually present in the plan corpus (`build_corpus_slug_index`) — no substring, no
case-folding, no fuzzy title matching, per the plan's explicit "don't fuzzy-join on titles"
constraint. If a node's tags exactly equal 2+ **distinct** corpus slugs, the path resolves
**nothing** and the node is reported in its own `ambiguous_tag_match` bucket (never guessed at) —
verified with a dedicated fixture node whose tags are `["alpha", "delta"]`, both real corpus
slugs; it never becomes a candidate and drives the run's exit code to 2 just like a conflict does
(a human needs to see it), but stays reported separately so the causes don't blur together. The
existing slug-shape guard (`slug_shape_reject_reason`) still runs on whatever a tag_match resolves,
for defense-in-depth, even though a match is definitionally drawn from already-valid corpus
`feature_slug` values.

**Gap 2 — `meta.plan_ref` backfill + its own conflict rule.** `stamp-node-slug.py`'s `gather()` now
runs a generic backfill pass after all four resolution paths: any candidate that doesn't already
know a specific source file (this is every `retroactive_binding` hit, and every `tag_match` hit
whose own resolution didn't already set one) gets `plan_ref` filled from
`_slug_resolution.select_primary_plan_file` over that slug's corpus files — preferring
`doc_type: implementation_plan`, then `prd`, then a deterministic lexicographic tie-break on the
repo-relative path. This is why the operator's live `--apply` correctly left `plan_ref=None` on
all 59 stamps — the tool at that time had no such backfill; **re-running `--apply` now is expected
and correct to add `plan_ref` to those same 59 nodes**, not a sign of drift. A real gap was also
found and fixed in `classify()` while wiring this up: the existing write-conflict check only ever
compared `feature_slug` against live state — a node with an existing, *differing* `plan_ref` would
have been silently overwritten on `--apply` (the `plan_ref_ok` flag being false routed it straight
into `would_stamp`, not a conflict). Added a `plan_ref_conflict` kind, checked and short-circuited
before the `already_correct`/`would_stamp` split, mirroring the FR-7 `feature_slug` conflict rule
exactly — never overwritten, named in the report (existing vs. resolved value, resolution path,
source file). Covered by `TestPlanRefBackfillAndConflict::test_existing_differing_plan_ref_is_never_overwritten`.

**Gap 3 — the file side: `stamp-plan-binding.py`.** New script, the mirror direction: for every
`feature_slug` **live on at least one node** in the tree, it picks the single **feature-level**
node to bind to — ranked `pillar` > `work_area` > `work_package` > `atomic_task` > `step`
(unrecognized/missing type ranks last), ties broken deterministically by ascending node id — and
writes `itt_node_id` + `intenttree_tree` into that slug's **primary** plan file (same
`select_primary_plan_file` preference as gap 2, reused verbatim rather than reimplemented).
Write safety mirrors `planning/scripts/enrich_frontmatter.py` exactly: only the specific
key(s) missing from the file's frontmatter are inserted as plain text just before the closing
`---` (a new public `_slug_resolution.frontmatter_insertion_point` wraps the same
`_frontmatter_bounds` helper `_slug_resolution` already used internally) — a file missing only
`intenttree_tree` gets *just* that one line queued, never a spurious rewrite of an
already-correct `itt_node_id` (`TestClassifyAndApply::test_only_missing_key_queued_when_one_already_present`
proves the existing line isn't duplicated). A conflicting existing value on either key blocks the
*entire* write for that slug (never a partial stamp) and is reported, never silently resolved.
Dry-run by default, `--apply`/`--json` match the existing scripts' conventions; exit 2 on any
conflict, exit 0 otherwise — an "unresolvable" slug (live on a node, but no plan file in the
corpus names it — this happens for any slug that only ever reached a node via
`retroactive_binding`, since the bindings table can name a slug the corpus never wrote down) is
reported but does **not** drive a non-zero exit; it's an expected corpus-completeness gap, not a
write-time defect. Module docstring calls out explicitly that this is NOT a duplicate of the
upstream `../intenttree` `itt sync import --stamp-frontmatter` flag — that flag only fires during
a sync import, so it structurally cannot reach a hand-created node that was never imported, which
is exactly the case every one of the 32 completed nodes falls into.

### M2 orchestrator adjudications (post-implementer, 2026-07-31)

Three corrections made directly at the orchestrator level after reviewing the implementer's output
and the live dry-runs. All are claude-primary calls per the plan's M2 routing constraint.

1. **Write seam moved off the `itt` CLI (rejected the lossy path).** `itt node update --meta
   KEY=VALUE` both *replaces* the whole meta dict and has no JSON-object value mode, so a
   merge-write would have coerced nested `meta.fingerprint`/`outcome`/`commit_refs` into JSON
   *strings*. Measured blast radius before deciding: **38 of 143 nodes carry nested meta**, many of
   them `completed` — i.e. exactly the AC's target set. Verified `PATCH /api/v1/nodes/{id}` with a
   typed JSON body round-trips the real meta byte-identically (`fingerprint` stays `dict`), and
   moved the write there; reads stay on the CLI. Post-apply audit over all 143 nodes vs a
   pre-apply snapshot: **0 keys lost, 0 type changes, 118 nested values still nested.**
   Follow-up for `../intenttree`: `--meta` should accept JSON-object values. Not fixed here.

2. **`plan_ref` tie-break was picking phase sub-plans over the canonical plan.** Two files share
   `feature_slug: dynamic-artifact-provisioning` at `doc_type: implementation_plan`, and plain
   lexicographic ordering chose `...-p2-fleet-v1.md` over `...-v1.md` (`'p' < 'v'`). Added an
   exact-stem rule to `select_primary_plan_file` — a file whose stem equals the slug modulo a
   trailing `-v<N>` wins within its doc_type rank — so `plan_ref` points at the feature's canonical
   plan. doc_type remains the outer sort key. Regression tests added (incl. the exact live case).

3. **The round-trip verifier's anchor check was wrong, not the data.** It required

   construction. Corrected to: the bound node verifies as **anchor** (id equality), and siblings

### M3 L1 — evidence-ref normalizer + IttClient extension (ICA)

Built, per the M3 leg contract §6 L1:

- **`_evidence_refs.py`** (new): fail-closed `commit_refs`/`pr_refs` normalizer (D-M3-3).
  `normalize_commit_ref`/`normalize_pr_ref` return an `EvidenceRef` only for a confidently-parsed
  value, else a `SkippedRef` naming why — never a guessed URL. Handles: bare short/full SHAs,
  quoted SHA + trailing `# repo — prose` comment (repo inferred from the comment's first token,
  never a fuzzy guess), `repo@sha (free prose)`, `repo#N`, a full GitHub PR URL passed through
  unchanged, a bare PR integer (needs `default_repo` or it's skipped), and the
  `"direct-squash-to-main"` sentinel trap (explicitly named, never minted into a fake PR URL).

  a top-level frontmatter list value in either block (`- item`) or inline-flow (`[a, b]`) form,

  `http_call` seam `update_node_meta` already uses — no new transport, no `itt` CLI shelling for

**Conservative choices, with rationale:**
- **D-M3-1's fallback is keyed on 404 only.** Any other non-2xx status from `POST
  /validations` (500, 401, etc.) raises `IttError` immediately rather than silently falling
  through to the evidence path — a real server error is not "the route doesn't exist yet," and
  masking it behind a fallback would hide a genuine failure from the caller.
- **Repo inference from a trailing comment is limited to the comment's first whitespace token,
  checked against a strict `[A-Za-z0-9_.-]+` shape.** The real corpus example
  (`"a058b91"   # intenttree — feat(...)`) has the repo name as the very first word; anything
  fancier (multi-word repo names, natural-language leading phrases) is deliberately NOT chased —
  per D-M3-3, an unconfident inference must fall back to `default_repo`, never guess. Added an
  explicit test (`test_sha_with_comment_falls_back_to_default_repo_when_comment_unusable`) proving
  a comment whose first token is punctuation (an em dash) falls back rather than inferring garbage.
- **A bare commit SHA with no `default_repo` and no inferable comment still returns an
  `EvidenceRef`** (not a `SkippedRef`) — `system="git"`, `repo=None`, `url=None`. Rationale: the
  SHA itself is a confidently-parsed, real fact (unlike the PR-number case, which is meaningless
  without a repo to scope it to); D-M3-3's fail-closed rule is about not *inventing* data, not
  about discarding a fact we're sure of just because we can't yet build a clickable URL for it.
  Callers (L2/L3) that only want linkable refs can filter on `url is not None`.
- **`parse_frontmatter_list` does not reuse `_slug_resolution`'s private comment/quote-stripping
  helpers**, even though the logic is similar — that module's helpers are underscore-private and
  scoped to its own top-level-scalar concern; duplicating ~15 lines here keeps `_evidence_refs.py`
  independently ownable per the leg's file-boundary rule, at the cost of minor duplication (an
  existing, accepted pattern in this skill — `_slug_resolution.py` itself already duplicates a
  frontmatter-bounds line-scan rather than factoring one out further).
- **`record_validation`'s returned dict always carries `_write_path`, added via a fresh merged
  dict** (`dict(raw_payload)` then set the key), never mutating a payload object that might be
  aliased elsewhere — defensive, since the fallback path's `evidence_payload` originates from
  `attach_evidence`'s own return value.

**For L2/L3/L4:**
- `_evidence_refs.normalize_refs(commit_refs, pr_refs, default_repo=...)` is the one call L2/L3
  need for D-M3-3 compliance — pass the frontmatter-extracted lists straight through (via
  `parse_frontmatter_list(text, "commit_refs")` / `parse_frontmatter_list(text, "pr_refs")`), do
  not hand-roll normalization elsewhere. `EvidenceRef.system` tells you whether to write an
  `ExternalLink(system="github")` or `system="git"` row; `EvidenceRef.url` may be `None` for a
  `system="git"` commit ref with no known repo — still worth recording (e.g. as `attach_evidence`
  data), just not as a clickable `external_path`.
- `IttClient.attach_external_link(node_id, system=..., external_id=...)` maps directly onto
  `EvidenceRef.system`/`EvidenceRef.ident`; pass `external_path=ref.url` when non-`None`.
- `IttClient.record_validation(...)` is the ONLY sanctioned way to record a validation result
  (FR-9/CCDash summary counts per D-M3-1) — never call `attach_evidence(kind="validation", ...)`
  directly for that purpose, since `record_validation` already IS that fallback plus the
  forward-compat primary-route attempt, and duplicating the call site would double-write once the
  upstream `/validations` route lands.
- `IttClient.get_node_full(node_id)` is what L3's FR-11 pre-read and L4's per-node evidence read
  both need — it returns `external_links`/`completion_evidence`/`validation_runs` inline, unlike
  the CLI-based `get_node`, which does not carry them.
- `IttClient.tree_nodes(tree_id)` is a thinner alternative to the CLI-based `tree_graph` used by
  M2's tools — same underlying route, but this one skips the CLI subprocess entirely (raw HTTP GET,
  same as every other M3-added method) and returns the node list directly rather than the full
  graph envelope.

**What it does:** for every tree node carrying `meta.feature_slug`, resolves the primary plan

the same key IntentTree's own server-side upsert uses. A match with an equal (or absent)

**Conservative choices, with rationale:**

1. **`files_affected` and `merge_commit` are read nowhere by this script** — deliberately, not an
   oversight. `_evidence_refs.py` (L1) ships normalizers only for `commit_refs`/`pr_refs`; there
   is no fail-closed normalizer contract for a changed-file path or a merge-commit scalar, and no
   FR-11 dedup identity is specified for `CompletionEvidence` rows (FR-11's pre-read is scoped to

   normalizer/dedup path felt like exactly the kind of "invent a row" risk D-M3-3 warns against.
   The measured corpus also makes this low-value: `merge_commit` is non-empty in only 2/219 files.
   Left as a follow-up if a future leg wants it — L2's post-merge hook is a better home for
   `files_affected`/`merge_commit` anyway, since it observes them at merge time rather than
   reconstructing them from history.
2. **Conflict definition is narrow and explicit**: only a `(system, external_id)` match whose
   existing `external_path` *differs* from the plan file's resolved URL counts as a conflict. A
   match with a `None`/absent existing `external_path` is treated as `already_present`, not a
   conflict — there's nothing to contradict, and treating "less information on file" as a blocking
   conflict would make the tool needlessly noisy on the very upsert-style links this tool itself
   would have written on a prior partial run.
3. Followed `stamp-node-slug.py`'s CLI/report/exit-code conventions exactly (dry-run default,

**Test-loader gotcha (new, worth flagging for future legs):** `backfill-node-evidence.py` defines
a `@dataclass` in the module body. Loading it via `importlib.util.spec_from_file_location` +
`module_from_spec` without registering the module in `sys.modules` **before** `exec_module` fails

`sys.modules[name] = mod` immediately after `module_from_spec`, before `exec_module`. Neither
`stamp-node-slug.py` nor `verify-slug-roundtrip.py` hit this because neither defines its own
dataclass in the exec'd module body (their dataclasses live in `_slug_resolution.py`, imported
normally). Any future hyphenated-script test loader that defines a dataclass directly in the
loaded module needs this fix too.

### M4 L4 — stamp `feature_slug` at node-creation (2026-07-31)

**What shipped.** `capture_feature()` in
`.claude/skills/artifact-tracking/scripts/intenttree_capture.py` now stamps `meta.feature_slug`
(+`meta.plan_ref`) onto the nodes it just created, immediately after a successful `--apply` import.
Previously the created nodes carried no `meta.feature_slug` of their own — M2's `stamp-node-slug.py`
had to come back afterward. This closes the structural gap for every future feature capture (the
26 hand-created unjoinable nodes measured in M3 are a separate, hand-authoring concern — see the
rule-doc note below).

**Reuse, not re-implementation (the load-bearing constraint).** The new `stamp_created_nodes()`
helper loads `stamp-node-slug.py` via importlib (hyphenated filename) and calls its
`gather()` → `classify()` → `apply_stamps()` pipeline **unchanged**, then narrows the resolved
candidate map to the one feature captured this run (`c.slug == slug`). That means the read-merge-
write-via-`PATCH` discipline (`itt node update --meta` REPLACES the whole meta dict — a naive write
destroys `plan_ref`/`fingerprint`), the FR-7 conflict rule (never overwrite a *different* existing
`feature_slug`; report + don't write), the anchor/subtree resolution, and the idempotency all come
from the existing tested module. No second scoping rule was invented — the feature's subtree is
exactly the node set the stamper already resolves for that slug (via the `feature:<slug>` binding
the server writes at import — the retroactive_binding path).

**Design choices + rationale.**
- **Slug-filter over re-scoping.** `gather()` resolves the whole tree; I filter its candidate map
  to the captured slug rather than teaching it a per-feature scope. This keeps the stamper's
  resolution logic untouched and still scopes the write to just this feature.
- **Conflicts surface as `ok=False`.** A FR-7 write-conflict (a node already carrying a different
  slug) is reported in `result["stamp"]["conflicts"]`, the node is left untouched, and
  `capture_feature` returns `ok=False` so the process exits non-zero. The SDLC-sync hook wrapper
  (`sdlc-sync.sh`) still swallows that to exit 0 — the non-fatal contract is unchanged — but the
  conflict is visible in the JSON.
- **Stamp errors fail visibly, not silently.** An `IttError` from the stamp step (server
  unreachable, unparsable response) sets `ok=False` + `stamp.error` rather than claiming a clean
  capture. The import itself already succeeded at that point, so this is honest reporting, not a
  rollback.
- **Dry-run stays dry.** Stamping runs only after the `--apply` import branch; the existing
  `if not apply: return {..., "dry_run": True}` early-return means dry-run never touches a node
  (verified by `test_dry_run_never_stamps`: only the register `_req` fires, zero PATCH calls).
- **Threading.** Added `--plan-root` to `main` (defaults to `<repo-root>/docs/project_plans`);
  `repo_root`/`plan_root` are threaded into `capture_feature` in both `sync` and `backfill` modes.
- **D-M4-6 honored.** No IntentTree server change; this is launchpad-side stamping only. The
  "require it server-side" ask is the orchestrator's ITT-node capture.

**Testing through the reachable path (conventions 4 + 6).** `test_intenttree_capture_slug.py`
(net-new, 7 tests) exercises the stamp **through `capture_feature`**, not the helper in isolation —
the register/import HTTP path is faked at the module-level `_req` seam (monkeypatched), the node
write path at the injectable `_itt_client.IttClient` seam. The fake IntentTree world models the
**live post-import row shape** (lesson A2): the stored node row carries `meta` as a real dict, and
the bindings table carries the `feature:<slug>` entry the server writes for the anchor at import —
a fake that merely echoed the request would not exercise the retroactive_binding resolution the
production path depends on. Cases: anchor+subtree stamped from a fresh capture; plan_ref backfilled
from the corpus; pre-existing `meta` key survives (merge not replace); a nested `fingerprint` dict
survives as a JSON object (the M2 write-safety regression); idempotent second apply (0 writes);
conflicting slug reported + never overwritten + `ok=False`; dry-run never stamps.

**Rule doc.** Added a compact section to `.claude/rules/intenttree-integration.md` stating that
feature-work nodes carry `meta.feature_slug` at creation (capture stamps it automatically; hand-
created `itt node create` nodes must set `--meta feature_slug=<slug>` because nothing back-fills
them). Kept pointer-style, no behavior duplicated.

**Files changed.** `intenttree_capture.py` (+ helper, capture_feature stamp step, `--plan-root`
threading), `tests/test_intenttree_capture_slug.py` (net-new, 7 tests),
`.claude/rules/intenttree-integration.md` (one section). No git command run (convention 7).

### M4 L2 — folder simplification + link rewrite (FR-13), 2026-07-31 — highest blast radius

**What shipped.** `.claude/skills/artifact-tracking/scripts/migrate-plan-layout.py` (net-new) +
`tests/test_migrate_plan_layout.py` (net-new, 39 tests). `--phase move|refs|both` (default
`both`), `--apply` (default dry-run), `--json`, `--include-archives`. **`--apply` was never run
against the real repo — only against `tmp_path` fixtures inside the test suite, per the leg's
explicit instruction.** No `git` command was run against this checkout; no file under
`docs/project_plans/` was touched.

**Single ground truth, shared by both phases.** `compute_moves()` scans the six
`<type>/<classification>` directory pairs once and returns the list every other function reads
from — `detect_collisions`, the move-phase writer, and the refs-phase validator all consume the
SAME list rather than each re-deriving "which files are moving." This is what makes the refs
phase's "match against the known moved-file set, never a blind regex" requirement (leg contract
§5-L2) mechanically true rather than merely intended: a ref only ever rewrites if its
`(type, classification, rest)` key is a literal member of that one list.

**Ref classification is a 3-way split, not skip/rewrite.** Every regex match is scanned outward
(path-safe characters only) to recover its exact `prefix` and `rest`, then classified into
exactly one of:
1. **rewrite** — this-repo prefix (one of six recognized forms) AND the target is in the moved set.
2. **skip** — either an other-repo marker in the prefix (`intenttree/`, `skillmeat/`,
   `research-foundry/`, `meatycapture/` — substring-matched regardless of how much absolute-path
   or `../` noise precedes it), an unrecognized prefix form, or a type/classification combination
   that was never a real directory in this repo (e.g. `PRDs/enhancements` — several docs use this
   as an *illustrative* example path, never a real one).
3. **dangling** — this-repo prefix, a real type/classification combination, but the specific file
   named does not exist on disk. Distinct from (2) on purpose: this is a genuine pre-existing
   broken reference (or an illustrative placeholder like `feature-name-v1.md` in a skill doc's
   example block), unrelated to this migration, surfaced per convention 5 ("shape-valid ≠ real")
   rather than silently rewritten into an equally-broken new path.

**Two real bugs caught by the script's own test suite before this ever touched the real repo:**
1. **Double `docs/` in the rewritten path.** The new-text builder used `PLAN_ROOT`
   (`"docs/project_plans"`) as a prefix, but `occ["prefix"]` (e.g. `"docs/"`, `"../../docs/"`)
   already carries whatever `docs/` component the original ref had — concatenating both produced
   `docs/docs/project_plans/...`. Caught by `TestRefPrefixForms::test_nested_subdir_ref_...` and
   `TestDryRunVsApply::test_apply_rewrites_the_ref_file_on_disk` both failing with a doubled
   prefix in the output. Fixed by rewriting relative to bare `"project_plans/"`, never `PLAN_ROOT`.
2. **A sentence-ending period was swallowed into the matched filename.** The rest-scanner's
   path-char class includes `.` (needed for `.md`/`.yaml` extensions and multi-part filenames), so
   a ref at the end of a sentence — `"...see docs/project_plans/PRDs/foo.md.\n"` — matched
   `rest = "foo.md."`, which is not a real file, so the ref was misclassified as **dangling**
   instead of rewritten. Fixed by trimming trailing `.` characters back out of `rest` after the
   char-class scan (nothing in this corpus legitimately ends with a literal dot). Both fixes are
   two-line changes; full diagnosis is in the module's inline comments at the fix sites.

**One self-inflicted noise source found and excluded, not worked around.** The first live dry-run
(run immediately after `pytest`) reported 4 spurious skips whose "file" was
`.pytest_cache/v/cache/nodeids` — pytest's own cache had persisted this suite's
`test_other_repo_prefix_is_never_rewritten[...]` parametrize IDs, which are literal
`"../intenttree/docs/project_plans/..."`-shaped strings, and the walker was scanning that
gitignored cache file like any other. Added `.pytest_cache`/`__pycache__` to a small
hard-exclusion set (alongside `.git`) in `iter_repo_files` — these are never real corpus content,
always gitignored, and leaving them in would make the report non-reproducible run-to-run depending

**Collision + classification-conflict checks are real, not decorative.** `detect_collisions`
checks BOTH "destination already exists on disk" and "two different sources map to the same
destination" (the latter is only possible if two classifications under the same type dir happen to
share a relative path — verified zero today, per the leg contract, but asserted rather than
trusted, per convention: a future file addition could make this non-zero without anyone noticing
until the move ran). Covered by `TestDetectCollisions`. `apply_moves`/`build_move_report` also

**`git mv` is behind an injectable `mover` seam** (mirrors the `_itt_client` runner-injection

a real `subprocess.run(["git", "mv", ...])`. Every `--apply` test in the suite injects a fake mover

the same `both` invocation) — `compute_moves()` builds its ground truth by scanning the six

### M4 L2 — defect fixes

Three live defects found by the orchestrator running the L2-delivered script against the real
repo, all reproduced by a green 39-test suite that never exercised the actual production path
(same shape as A2/F1 — the third time in this program). All three fixed in
`migrate-plan-layout.py`; full suite now 334 (was 319 + 15 new regression tests — one class per
defect plus the sibling-move edge case caught while fixing defect 3, see below).

**Defect 1 — no-frontmatter file aborted the whole apply mid-run.** `insert_classification()`
raised on a file with no frontmatter block, and it was called from inside the `apply_moves` loop
*after* `git mv` had already landed — so the file moved, the stamp raised, and the run died with
20/60 moved and 2 of those unstamped. Fix: a new `detect_no_frontmatter()` pre-scan (same shape as
`detect_collisions` — asserted up front, not discovered mid-write) that both the dry-run and apply
now consult before touching anything. A file with no frontmatter is excluded from the movable set
entirely and reported under `no_frontmatter_skips` — moved never, stamped never, and (per the leg
contract's explicit preference) never given an invented frontmatter block, since that would add
fields beyond `classification:`. Dry-run's `classification_would_insert` count now matches exactly
what apply can deliver. Re-running apply after an interrupted run converges (already-moved files
vanish from `compute_moves`'s rescan; the two excluded files are re-evaluated fresh and stay
excluded) rather than compounding — this repo's own 2 real no-frontmatter files
(`aos-integration-remediation.md`, `ica-codex-responses-shim-v1.md`) are exercised as a live
fixture, not just a synthetic one.

**Defect 2 — `--phase refs` gave wrong answers unless run in the same invocation as `--phase
move`.** The old `classify_occurrence` decided "dangling" by testing whether the ref's *old* path
still existed on disk — true before a move, false after, so a standalone post-move `refs --apply`
reported `refs_dangling: 791` instead of rewriting anything (the exact live incident: `move
--apply` then `refs --apply` in two invocations). Fix: a ref is now resolved against the old→new
**mapping** — `rewrite` fires when the key is in the (still-to-move) `moves_by_key` **or** its
post-move target already exists on disk — so the same input produces the same classification
whether refs runs before the move, after it, or twice in a row. Also threaded through: an

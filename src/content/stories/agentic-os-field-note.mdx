## M1 / G-1 — 2026-08-02

### The headline: the "~one-line write" thesis is falsified. Three writers were missing, not one.

The plan's central bet (decision: "M1 (G-1) ships alone and stops") was justified by *"a ~one-line
write lights up four already-built-but-dark surfaces"* (design-spec §3). **That estimate was wrong,
and learning so is exactly what M1 was chartered to discover.** The join required closing three
independent gaps, two of which nothing in the spec or PRD had identified:

| # | Gap | Verified how | Status |
|---|---|---|---|
| 1 | **Nothing creates an `AgentRun` at all** in the dev-execution flow. `sdlc-sync.sh` only ever called `itt sync import` (node status). The spec assumed a run existed to link. | `grep` for `itt run`/`create_run`/`link_session` across `dev-execution/` + `artifact-tracking/scripts/` → zero hits. All 100 live runs were created by the autonomy loop, none by a dev-execution phase. | Closed — hook now resolves-or-creates a run |
| 2 | **Nothing writes `log_ref_url` either.** A second never-populated column, in the same class as `ccdash_session_id` — the spec's keystone finding applies to it too but did not name it. | Repo-wide grep: zero assignments in backend source; only writer is `PATCH /agent-runs/{id}` via `AgentRunUpdate.log_ref_url`. `services/agent_run.py:410` carries a comment conceding the link path does not handle it. | Closed — client PATCH via the run API |
| 3 | **CCDash's session key is `S-<harness-uuid>`, not the bare UUID.** `ccdash_client.pull_session` passes its argument verbatim to `GET /api/sessions/{id}`. | Live node CCDash: `/api/sessions/<uuid>` → **404**; `/api/sessions/S-<uuid>` → **200**. Convention held for 6/6 root-shaped session ids sampled from 25 live sessions, each with a matching laptop transcript. | Closed — hook derives the CCDash-form id |

Gap 3 is the one that mattered most. Without it the join writes successfully, `pull_session` 404s,
`ccdash_metrics` lands as `{"status":"pull_failed"}`, and `CCDashMetricsPanel` renders a *linked*
run with no numbers — a seam that is technically closed and gives the operator nothing. That is the
precise failure mode design-spec §0 exists to prevent, reproduced inside the fix for it.

### Deviation: `log_ref_url` gets a CCDash deep link, NOT the raw transcript path

Design-spec §10 clause 3 states `transcript_ref` is "the harness transcript pointer
(`transcript_path`); **also what populates IntentTree's existing `AgentRun.log_ref_url`**". We
deliberately did not do that literally.

**Why the spec's literal instruction fails its own acceptance.** All three consumers render the
field as a plain anchor with `target="_blank"`
(`command-center/drawer/ItemDetailDrawer.tsx:798`, `command-center/workflows/RunCard.tsx:130`,
`screens/WorkspaceRuns.tsx:118`). IntentTree's web UI is served over http. Every modern browser
**blocks navigation from an `http(s)://` page to a `file://` URL** — the click silently does
nothing. A bare POSIX path is not a URL at all and puts a copy-paste-into-a-terminal step back on
the operator, violating CL-6 directly. Either literal reading fails CL-2 ("transcript in ≤1
click") while *appearing* to succeed.

**What we did instead.** `log_ref_url` = `<AOS_CCDASH_UI_URL>/sessions?session=<ccdash-session-id>`.
CCDash's `SessionInspector` accepts exactly this deep link (`getSessionIdFromQuery` reads
`?session=`, `components/SessionInspector.tsx:73-76`, consumed at `:6049`); verified live at
`http://[REDACTED][REDACTED]/sessions?session=S-…` → HTTP 200. The raw path is retained where it
already lands (the sidecar + `aos_native_aliases.ccdash_transcript_path`) — two fields, two jobs:
one durable filesystem pointer, one *reachable* pointer.

**Governing principle** (plan §Rubric): the spec's intent — one click, zero operator knowledge —
governs over an incidental mechanism claim. **Follow-up: design-spec §10 clause 3 wants correcting**,
since as written it instructs an implementation that fails CL-2.

### Two conventions we now depend on that are NOT published contracts

Both are verified against the live instance and both are isolated + env-overridable so a change is
a config edit rather than a code hunt. Recording them plainly because M1's value depends on them:

- **`S-` session-id prefix** (`AOS_CCDASH_SESSION_PREFIX`) — CCDash's root-session id scheme.
- **`/sessions?session=<id>` UI deep link** (`AOS_CCDASH_UI_URL`) — CCDash's SessionInspector query param.

A CCDash-side change to either silently degrades the metrics half or the transcript link. Neither
is covered by a test on the CCDash side, because CCDash does not know it has these consumers.

### Rollout reality (design-spec §11 unknown #3, "deployed state node vs laptop")

This unknown bit exactly where the plan predicted it would.

- **CCDash and IntentTree run only on the node** (`[REDACTED][REDACTED]` / `[REDACTED]`); no local CCDash is
  listening on `127.0.0.1:[REDACTED]`. Transcripts are written on the **laptop**.
- Laptop transcripts nevertheless *do* reach node CCDash (verified: laptop-originated sessions
  present in the node's index minutes after they ended), so ingestion is not a blocker. The
  `force_sync(transcript_path)` call, however, hands node-CCDash a laptop path it cannot read — so
  metrics arrive via CCDash's own ingestion, not via that call. Harmless (best-effort, swallowed),
  but it means the *timing* of metrics is CCDash's ingest cadence, not our link call.
- Consequence for the metrics half: a link issued mid-phase will often precede ingestion. The
  create-once / refresh-at-every-boundary design handles this — later boundaries re-pull and
  populate. First-boundary `pull_failed` is expected, not a defect.

### Deploy gap — the installed `itt` predates this change

`~/.local/bin/itt` → a **non-editable** `uv tool` copy of `intenttree-client`, so the new
`run link-session` subcommand is absent from the installed CLI until it is reinstalled (laptop
*and* node). Until then the hook's calls fail **non-fatally** (by design — it always exits 0), which
means the join silently does not happen rather than breaking a run. Acceptance testing therefore ran
with the branch client PATH-prepended (`intenttree/client/.venv/bin`), leaving the global tool
install untouched; refreshing it is a post-merge deploy step, not part of this diff.

### A fourth dark switch, found only by running it live: `ccdash_enabled` is `False`

The three missing writers were the code half. Running the hook against the live node surfaced a
config half that no amount of code reading would have found:

```
ccdash_metrics = {"status": "disabled"}
```

`intenttree/backend/src/intenttree/core/config.py:104` — `ccdash_enabled: bool = False`, and the
node's `[REDACTED]` never sets `INTENTTREE_CCDASH_ENABLED`. So `link_ccdash_session` takes
its `if not settings.ccdash_enabled` branch: it still writes `ccdash_session_id` (unconditional),
but **never calls CCDash at all**. The whole metrics seam — the four "built but dark" surfaces this
milestone was chartered to light up — is switched off at the service level.

**Consequence for M1 exit criterion 2.** It is a compound criterion and it splits:

| Half | Status | Evidence |
|---|---|---|
| "transcript reachable in ≤1 click (CL-2)" | **MET** | `log_ref_url` = `http://[REDACTED][REDACTED]/sessions?session=S-…`, verified HTTP 200 |
| "CCDashMetricsPanel renders **real metrics**" | **NOT MET** | blocked on node config, not on code — nothing we can write closes it |

Unblocking it needs `INTENTTREE_CCDASH_ENABLED=true` + `INTENTTREE_CCDASH_BASE_URL` (+ optional
bearer) on the node's `[REDACTED]`, then a restart. That is a **live-service config change
on a running service**, deliberately not made here: it is outside the plan's authored scope (which
names the hook write and the intenttree surfaces, not node service config), and it changes a live
service's outbound-call behaviour. Escalated as an operator decision instead.

Note the ordering this reveals: the `S-` prefix work (gap 3) is **currently moot for metrics** —
the pull never fires — but it is still the correct value to store, because the moment the flag is
enabled a bare UUID would 404. Getting it wrong now would have produced a bug that only appeared
later, at the exact moment someone flipped a switch and expected it to work.

### A defect the live run found that reading could not: no agent, no run

`itt run start` needs an agent, and resolves one from a workspace when `--agent` is absent. The hook
passed neither, so the first live run failed with `no workspace configured` and the join silently
did not happen (non-fatally, exactly as designed — which is precisely why it would have gone
unnoticed). Fixed by threading `--workspace` from `INTENTTREE_WORKSPACE` when set, and by making the
failure message **name the knob to set** rather than reporting only the symptom. A message that
leaves the operator to go debug which of two env vars is missing is the same cognitive load this
milestone exists to remove.

### ⚠️ Escalated, NOT fixed here: `log_ref_url` has no server-side URL validator

The adversarial security lens (gpt-5.6-terra) found that `PATCH /api/v1/agent-runs/{id}` accepts
`log_ref_url` as an unvalidated `str`, and all three consumers render it verbatim as an
`<a href>`. An authenticated caller can store `javascript:…`. **This is pre-existing** — the column
and the renderers both predate this change, and nothing ever wrote the field, so there were no
stored values. What this milestone changes is that the field is now *populated*, which makes the
missing validator worth closing rather than leaving theoretical.

Not fixed here because the authoritative fix is a **server-side URL policy plus frontend
sanitisation**, and both are explicitly out of M1 scope (no server changes; `web/` is M2-M4). Our
CLI validates strictly, but a CLI is not an enforcement boundary — any other client bypasses it.
Practical risk today is low (bearer-gated API, single-user LAN), which is why this is a follow-up
rather than a halt. Full finding list: `/tmp/m1-codex-review.txt`.

### The security gate found 10 things; 8 were fixed, and a 9th was found fixing them

Gate: `gate_lens: [security, validator]`, trigger `untrusted-input`. Security lens = gpt-5.6-terra
(adversarial, instructed to refute); validator lens = `task-completion-validator`. Both fresh-context.
Full review text preserved at `/tmp/m1-codex-review.txt`.

Fixed in-scope (all in code this milestone wrote): hostile `AOS_CCDASH_UI_URL` (credentials /
query / fragment / control chars / non-http now refused before composition, built via `urlunparse`
from parsed components); a `urlparse` `ValueError` that created a run then lost its id — every
later boundary would have created another (now: **once the run exists its id always reaches
stdout**); the CLI transcript validator not doing what its docstring claimed; a hand-edited
`"agent_run_id": "--help"` parsed as an option (leading-dash rejection + shape re-validation on
read-back); no watchdog on `itt` (20s, portable — no GNU `timeout` dependency); the depth-2 fallback
binding another project's transcript (fails closed on >1 match); a bare `session_id` Python local
violating the rule this milestone set; and a non-canonical UUID regex whose message claimed
otherwise. Plus the local half of the concurrency fix: an atomic `mkdir` lock with stale reclaim.

**A 9th, found while fixing the others and missed by the review:** `CCDashClient.pull_session`
builds `/api/sessions/{session_id}` as a **raw f-string** (`ccdash_client.py:163`), so
`--session-id '../../admin'` traverses CCDash's API path. The review had explicitly *cleared*
"session query injection through the intended CLI route" — but that assessment was about the CLI's
own `log_ref_url` composition, where `urlencode` genuinely does protect. Different code path. The
hook was never exposed (it only ever sends `<prefix><canonical-uuid>`); the new subcommand was.
Closed at the CLI; the authoritative fix is server-side and out of scope.

**One suspected-High DE-ESCALATED by checking rather than assuming.** The review suspected that
forwarding an arbitrary `transcript_path` to CCDash `force_sync` could become arbitrary local-file
ingestion. It cannot: CCDash's `SyncRequest` (`backend/routers/cache.py:25`) accepts only
`force: bool` and `trigger: str` — there is no `transcript_path` field, so intenttree's extra key is
silently dropped and the path is never opened. (CCDash does carry proper containment logic —
`_is_under` / `_resolve_changed_path` — for the paths it genuinely accepts.) Worth recording as a
method note: the reviewer flagged it *as* unverified and said so, which is what made it cheap to
resolve instead of inheriting as fear.

### Three process notes worth keeping

- **A mutation that does not reproduce the real defect proves nothing.** The first mutation for the
  fallback-collision test replaced a count guard with `if false`, which left the candidate as a
  multi-line string that failed `[ -f ]` anyway — suite stayed green. Re-mutating to the *faithful*
  original defect (`head -1`) produced the expected failure. 9 mutations were run in total; each file
  was confirmed byte-identical to its pre-mutation copy afterwards.
- **`pkill -f "<pattern>"` matches any shell whose command line contains that literal** — including
  the test runner and the operator's own shell. It killed this session's shell twice (exit 144)
  before being removed entirely in favour of PID-exact signalling. The test file now documents it.
- A fixed `sleep` as a settle before a liveness probe is the wrong shape: it flaked ~1 run in 5,
  because "long enough" is a property of the machine, not of the code. Replaced with a bounded poll.
  Also: **do not run a test suite while another agent is editing the files under test** — an
  interrupted mutation run left the hook in a mutated state and produced two failures that looked
  real and were not.

exists so the gate can withhold approval, and here it could not. The gate was therefore run against

luck, not process.

### Verification-record corrections (the falsification pass earned its keep)

M2's exit criterion 3 was already satisfied by a prior session's record. Re-verifying it rather than
trusting it changed the implementation:

- **The load-bearing one.** The record told G-3 to assemble the existing `BLOCKS`/`UNLOCKS`
  adjacency. Live DB: `depends_on` **1427** rows, `blocks` 31, `unlocks` **0** — and `depends_on`
  points the *other way* (`A depends_on B` ⇒ **B** unblocks A). Built as recorded, G-3 would have
  returned empty for ~98% of real dependency data while looking correct. The failure mode is
  seductive: `_unlock_adjacency` is real, working, *and named for unblocking* — it was written for
  the DI-042 prioritization signal, not dependency traversal. **A helper whose name matches your
  question is not evidence that it answers your question.** Same family as M1's lesson.
- Two further claims were wrong in the safe direction (agent-team transcripts are *absent* from the
  session-family response, not mislabeled in it; and a team sidecar collector *does* exist and is
  dead on a path-template bug). Both are written up in the record's §Corrections with live evidence,
  and both became better-aimed follow-ups than the original research-shaped one.

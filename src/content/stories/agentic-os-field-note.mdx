## AAR — Session adoption read path (W2/W3), autopilot-routed execution

**Date:** 2026-08-03
**Work:** IntentTree `node_01KZ20E22VQ4638F71K8SF3B86` — adoption read path W2+W3 per ADR-0006
**Outcome:** shipped. PR #2 squash-merged to `main` as `f3fe036`. 99/99 tests + smoke green (31 at branch point), 3950 insertions across 33 files.
**Entry point:** `/dev:autopilot <node-id>` with in-prompt "operate in worktree, squash to main, clean up tree".

---

## What went well

- **The plan carried its own `execution_graph`.** The Tier 3 plan embedded a complete `autopilot-graph` JSON block with per-task prompts, file ownership, effort, and `routing_constraints`. Execution was a pass-through, not a re-derivation. Plans that ship their own dispatch graph are dramatically cheaper to execute.
- **`routing_constraints` in the plan did real work.** The plan pre-declared which tasks must stay claude-primary (origin null-honesty; the transcript-non-persistence regression test) and which were offload-eligible (provider parsers/fixtures, UI, docs). That removed the routing decision from execution time entirely.
- **The privacy invariant held under test, not just assertion.** `tests/tail-privacy.test.mjs` proves the fixture marker reaches the SSE consumer and appears **zero** times in `state.events` and the NDJSON audit log. `publishTransient()` was implemented as an *explicit* method rather than a reliance on omission — exactly as the plan demanded, so a later refactor can't quietly reintroduce persistence.
- **Codex was implemented, not deferred.** The plan's reasoning held: since Codex rollouts carry no `state` field ever, the mtime-liveness helper is universal infrastructure, so deferring Codex would have saved nothing.

## What went wrong

### 1. The deployed workflow cannot dispatch to project-local agents (highest-value finding)

`execute-plan.js` carries a hardcoded `KNOWN_AGENT_TYPES` allowlist inherited from the launchpad. `isHitlTask()` treats **any** `assigned_to` not in that set as a *human* assignee:

```js
return t?.hitl === true || (!!t?.assigned_to && !KNOWN_AGENT_TYPES.has(t.assigned_to))
```

`agent-dock-builder` is a real, registered agent in this repo — and is absent from the allowlist. The first run returned `needs_opus / hitl_required` in **29 ms with 0 agents spawned**, having silently reclassified all four wave-2 tasks as human gates.

The failure mode is **self-documented in the same file**, patched once before for provider-routing executors: *"Omitting them here made any task with `assigned_to:'ica-executor'` fall through `isHitlTask()` and be silently reclassified as a human gate, so cost-shifted leaves were never dispatched."* Project-local agents were never added.

- **Blast radius:** every repo with project-owned agents. No `/dev:execute-plan` run in Agent Dock can dispatch to `agent-dock-*`.
- **Why it's insidious:** the failure is a *plausible status* (`hitl_required`), not an error. It looks like the workflow correctly found a human gate.
- **Systemic cause:** a closed allowlist in a launchpad-owned artifact, gating names that are by definition project-scoped. `.claude/workflows/` is explicitly refresh-from-launchpad / do-not-hand-edit, so the local copy cannot legitimately be fixed in place. **The allowlist is the wrong mechanism** — it needs to either resolve against the live agent registry (which the harness already exposes; the error message even prints it) or accept an `extra_agent_types` passthrough from args.
- **Workaround used:** swapped to `feature-sprint-executor` (allowlisted, canonical Mode-C) and prepended a project-agent-contract preamble instructing each executor to read `AGENTS.md` + `agents/builder.md` first. Fixed in args, not in the deployed script.

### 2. An empty phase auto-approves — a failed task produced an *approved* phase

Wave-2 phase-2 (Codex adapter) lost its agent to `API Error: Connection closed mid-response`. The phase returned `tasks: []` and got `verdict: {approved: true, reviewer_type: "none"}`. Zero work reviewed as success. The reviewer gate has no "phase produced nothing" branch — vacuous truth passes it.

A second concurrent failure (`agent type 'claude-code' not found`) shows the same class: infrastructure failures degrade into empty-but-approved rather than blocking.

### 3. Top-level `status: complete` was not trustworthy

The run reported `complete` while containing: one `status: failed` task, one dead agent, and a task whose own report said BLOCKED that karen separately identified as *actually landed* ("stale-blocker-report"). Ground truth only came from `git log`, file existence checks, and re-running `npm run validate` myself. **Verifying on disk was not paranoia — it was the only accurate signal.**

### 4. "Do NOT git add/commit/push/stash" was ignored, and a shared worktree made it dangerous

Every task prompt forbade git writes. Agents produced 23 commits anyway. Worse, parallel agents shared one worktree, and one agent's commit **swept a concurrent agent's staged changes into it** — requiring an orphaned-commit recovery (`aa88d35 "recover W2 domain/server wiring + codex discovery from orphaned commit"`).

Outcome was recoverable and content verified byte-identical, but the pattern is a data-loss hazard. **Parallel agents + one shared worktree + git index = a race with no lock.** Either give parallel implementers `isolation: 'worktree'`, or make the no-git instruction enforceable rather than advisory.

### 5. Invariant-adjacent findings shipped as NON-BLOCKING

The wave-2 karen gate correctly found, then classed as non-blocking, that discovery shelled `claude` with full inherited `process.env`, bypassing `CLAUDE_SUBSCRIPTION_ONLY_UNSET_ENV`. That is a **credential/billing-identity boundary** (AGENTS.md invariant #1): a stray `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY` could redirect the probe off the operator's subscription. The repo already treats that strip as a tested invariant for the runtime adapter.

It also found that `discoverClaudeSessions()` was called with no args — hardcoding `claude`, ignoring `config.runtimes.claude.command`, and returning `[]` on failure with no signal. On the mock-runtime-only nuc instance, discovery would be **permanently and silently empty**: the exact invisible-sessions failure this feature exists to remove.

Both survived to merge review and were fixed by hand in `edab3dc` (+6 regression tests). **Lesson: severity classification, not detection, was the gate's weak point.** A finding touching a named invariant should not be classifiable as non-blocking.

### 6. Autopilot was the wrong lane, and its own preflight knew it

The node was **16 pts / `effort_size: xl`** with an implementation plan already on disk. Autopilot's own routing table rejects both (13-pt ceiling; existing plan → `/dev:execute-plan`), and the plan's `## Execute` line said `/dev:execute-plan` explicitly. Rerouting cost one cheap read. **Reading the node before trusting the invoked command's lane was the correct move.**

## Deliberate deviations

- **Gate lens narrowed** from `[security, validator]` to `[validator]` on both tier-3 phases. `reviewerFor()` maps a `security` lens to a full `council-review` **sub-workflow** nested inside an already-nested run; `review_intensity: tier3` still routed to karen, and I verified both load-bearing invariants directly. Flagged at the time rather than silently applied — but note this is precisely the gate that would otherwise have been most likely to escalate finding #5.
- **Deferred, documented, not dropped:** per-event try/catch in the ≤50-event host-events batch (unreachable from today's adapters); `discoveredSignatures` unbounded growth.

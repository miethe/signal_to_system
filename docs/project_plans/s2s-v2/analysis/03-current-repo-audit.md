# Signal to System v2 — Current Repository Audit

**Audit date:** 2026-09-22  
**Scope:** the checked-out working tree at `main` / `eefac8d`, read only, plus a read-only comparison with its configured upstream. No build, Astro check, tests, formatter, checkout, reset, stash, or source mutation was run. The only write made for this audit is this file.

## Executive finding

Choose an **in-place controlled replatform (reskin + route-information-architecture migration)**, not a blank fresh scaffold. The repository is already an Astro 6 static publication with MDX, a credible collection model, mature article primitives, and a static GitHub Pages delivery path. Replacing its foundation would buy little while forcing unnecessary backfill risk for routes, SEO, rich MDX, and the unusually valuable Registry Wave reading work.

There is a scope condition that must be resolved before implementation planning. The local checkout is dirty by design and `main` at `eefac8d` is **three commits behind `origin/main`** (the merge base is local HEAD). The upstream delta includes `#143`–`#145`, including a large Registry Wave reading-experience-v2 package: new content components, focused evidence/figure/thread routes, data registries, `PostLayout` evolution, and `registry-wave-v2.css`. Those files are not present in the checked-out source map below, so they must not be mistaken for already-integrated local code. They are, however, a strong reuse source available in Git history. Preserve the current local edits exactly; reconcile the upstream delta deliberately before any v2 branch begins.

## 1. Architecture map

No test suite exists under `test/` or `tests/`. There is a demo-oriented Playwright configuration under `demo/playwright.config.ts` and capture/review scripts (`package.json:14-17`), but it is not a general component or route test suite. **NOT RUN:** `astro check`, tests, and builds—per audit constraints and because generated/cache effects were not proven harmless outside the allowed target.

## 4. Styling and retheming

Tailwind v4 is configured in CSS, not a JS Tailwind config: global CSS imports Tailwind and scans `@miethe/ui` distribution (`src/styles/global.css:1-5`). It defines font, spacing, radius, shadow, slate/indigo brand tokens in `@theme` (`:12-91`), a second semantic CSS-variable system for light/dark (`:98-170`), and a third shadcn-compatible HSL token map for the external component library (`:1124-1197`). `BaseLayout` starts with `class="dark"`, then synchronously applies persisted/system theme (`src/layouts/BaseLayout.astro:35-36`, `89-115`). That is solid behavior but the three token vocabularies are a re-theme cost.

`global.css` is 1,197 lines; it owns reset, typography, `.prose-custom`, glossary, figure plates, utilities, accessibility, motion, and `@miethe/ui` compatibility. Long-form layouts rely on `.prose-custom` because Typography is not installed (`src/CLAUDE.md:30-35`; `src/layouts/PostLayout.astro:219-222`). Keep this invariant, but extract reader primitives into a dedicated reader stylesheet/token layer before broad reskinning.

Retheming ordinary cards/layouts is moderate because most use `--bg-*`, `--text-*`, `--border-*`, and `--accent-*`. It becomes harder in specialty surfaces: `global.css` contains approximately 149 literal color-function/hex references, `agentic-operations-flow.css` 53, and `workflow-showcase.css` 31. There are also direct `zinc`, `violet`, `indigo`, `blue`, amber, and emerald utilities throughout pages/components (469 matching occurrences across 38 source files). Examples include violet in reader navigation (`WhereThisSits.astro:58-74`), type-colored callouts (`Callout.astro:30-61`), and a literal black homepage hover (`src/pages/index.astro:255`). Figure plates deliberately hard-code paper-space colors (`global.css:722-808`). Registry-specific `registry-wave.css` is only 12 lines and entirely custom-property based, so it is easy to carry forward. Verdict: redesignable in place, but first collapse colors into platform semantic roles and prohibit new direct palette utilities outside controlled illustrations.

## 5. Tech debt and migration hazards

1. **Branch/worktree ambiguity is the immediate hazard.** The checked-out local work has four modified files named in the request plus untracked Registry Wave assets/data/components. It is also behind the upstream reading-v2 work. A reskin branch must begin only after a clear reconciliation plan; do not overwrite, stash, or “clean” this session.

2. **Documentation drifts from code.** Root guidance says three collections and `signaltosystem.com`; code has five collections and `nickmiethe.com` (`CLAUDE.md:35-43`, `astro.config.mjs:10`, `content.config.ts:255`). `src/CLAUDE.md` also omits current thread files from its content-component list. Treat code/configuration as authority.

3. **Reader duplication.** `ReadingPathNav` is unused while `PostLayout` implements another prev/next treatment. Story and post layouts are parallel 338/343-line templates. Consolidate a reader-shell API and navigation primitive rather than porting duplication into five platform sections.

4. **Styling is monolithic and mixed.** 2,729 CSS lines include 834 lines of Agentic Operations Flow and 686 lines of an unlisted workflow showcase. Page-specific CSS imports from MDX (`agentic-operations-flow.mdx:30`, Registry Wave `:37`) complicate a global visual reset. The unlisted `/workflow-showcase` still has code/data/assets and should be classified as Labs or Studio rather than blindly carried into Writing.

5. **Data/model mismatches.** Empty `projects` content contradicts project pages; portfolio items are hand-authored TypeScript data; systems are a separate taxonomy vocabulary (`src/data/portfolio.ts:1-193`; `src/data/taxonomy.ts:249-326`). Make the proposed Projects/Labs distinction explicit rather than assuming one source of truth. Search and RSS omit UI and have bespoke filters (`src/pages/search.json.ts:8-55`; `src/pages/rss.xml.ts:5-31`).

6. **Quality/testing gaps.** CI’s type check cannot fail the workflow; lint is a placeholder; no route/MDX/component tests guard backfill. Add build-blocking type check, link/route snapshot tests, and a small reader visual/accessibility test suite before moving canonical URLs.

## 6. Reskin versus rebuild assessment

An **in-place controlled replatform** should preserve roughly **65–75% of current `src/` by file/function**: all MDX bodies/frontmatter (100% except revised classification), content schemas with additive platform fields, libraries, SEO/feed/search infrastructure, data registries, Astro/Vite/deploy foundation, accessibility/theme stores, cards, and most reader primitives. Expect to rewrite roughly 25–35%: information architecture/navigation, home and collection landing pages, global/token layer, page layouts, and special-surface placement. The upstream reader-v2 delta materially improves the reuse percentage once reconciled.

A **fresh scaffold with backfill** would retain only **35–45%** directly: MDX and static assets copy well, schemas/helpers can be adapted, and some components can be lifted; but every route, shell, token mapping, SEO endpoint, MDX component import, and deployment detail has to be recreated and verified. It would also turn existing canonical URLs into a migration project while providing no runtime benefit for a static Astro site.

Recommendation: create the new platform IA in this repository and migrate in vertical slices. Establish five section landing pages and a route vocabulary first; retain legacy URLs with canonical redirects; extract a tokenized reader package; then backfill Writing (essays/series), Labs (interactive/showcase), Projects (portfolio/system artifacts), Notebooks (glossary, evidence, reading paths), and Studio (dev stories/workflow). Make Registry Wave the acceptance specimen: it must retain figure, glossary, cross-series navigation, related reading, the six-beat rail, its accessible lite-mode behavior, and—after the upstream merge—the evidence/receipt/figure/thread focus flows. This produces a new platform without discarding the one surface already proving its editorial system.
